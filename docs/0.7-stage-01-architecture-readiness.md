## 2. Existing Architecture

CIVORA follows a **hexagonal/onion architecture** with a consistent package layout per domain:

```
internal/<domain>/
├── domain/          # Entities, value types, validation (pure, no I/O)
├── application/     # Application services (orchestration, transactions, audit)
├── api/             # HTTP handlers and route registration
└── infrastructure/postgres/  # PostgreSQL repository implementations
```

### Cross-cutting packages

| Package | Role |
|---|---|
| `internal/shared` | Shared interfaces: `CaseFinder`, `UserChecker`, `PersonFinder`, `FormSubmissionFinder`, `FormKeyResolver`, `SubmissionLister`, `FieldDiscoverer`, `CaseUpdater`. Plus `RecordAuditEventInTx`, `StrPtr`, `WriteSuccess`, `WriteError`, `WritePaginatedSuccess`. |
| `internal/middleware` | JWT auth (`AuthRequired`), `RequireSameTenant` (JWT org must match URL orgId), `RequireAnyRole` (role gate), `RequestID`, `BodySizeLimit`, rate limiting, idempotency, recovery, security headers, CORS. |
| `internal/server` | HTTP server setup, chi router, health/readiness, static FS mounting. |
| `internal/audit/domain` | Hash-chained, tamper-evident audit events. `AuditEvent` with SHA-256 hash chain, `VerifyChain`, `RecordEventParams`. Schema-isolated in `audit.audit_events`. |
| `internal/audit/application` | `AuditService` implementing `EventRecorder` with `RecordEvent` and `RecordEventInTx`; retention purge. |
| `internal/config` | Environment-driven config (DB, auth, audit, server). |
| `migrations/` | 31 SQL migrations (0001–0031), embedded via `//go:embed` in `migrations/embed.go`. Custom `splitSQL` supports dollar-quoted strings. |
| `internal/database` | `InTransaction` helper, `Migrator`, `BuildDSN`, `waitForDatabase`. |
| `cmd/civora/main.go` | Server entry point; wires all domains into the chi router. |
| `cmd/verify_identity/main.go` | Standalone build-time integrity verification (Ed25519). |
| `internal/identity` | Ed25519 project identity protection; `MustVerifyIntegrity()` called at startup. |

### Authorization Model

- **Authentication:** JWT bearer tokens containing `sub` (user ID), `organization_id`, `role`, `iss`, `iat`, `exp`, `jti`.
- **Tenant isolation:** `RequireSameTenant` middleware enforces that the JWT's `organization_id` matches the URL `{orgId}` parameter. Every repository query is additionally scoped by `organization_id`.
- **Role-based access:** Routes use `RequireAnyRole("admin", "staff")`. Some endpoints (e.g., case statistics) require specific roles; others allow any authenticated tenant member.
- **Rate limiting:** Per-user, 20 req / 5 min burst (configurable).
- **Request IDs:** Every request gets a unique ID propagated to audit events.
- **Body size limits:** Enforced via `middleware.BodySizeLimit`.

### Audit Infrastructure

- Audit events stored in `audit.audit_events` (dedicated `audit` schema, not `public`).
- Each event is SHA-256 hashed with a `previous_hash` link, forming a tamper-evident chain per organization.
- `VerifyChain(events)` validates hash integrity and chain linkage.
- Audit vocabulary is constrained by a CHECK constraint (`valid_audit_action`).
- The existing vocabulary (migration 0031) includes `evidence.added` and `evidence.deleted` but **no verification events** (e.g., no `evidence.verified`, `evidence.rejected`, `evidence.needs_review`).
- Every domain write operation records an audit event inside the same transaction via `shared.RecordAuditEventInTx`.

### Terminology: "service_request" = "case"

Throughout the codebase, `service_request_id` is the column name used as a foreign key to `cases(id)`. The Go domain type is `casesdomain.Case`. "Service request" and "case" are the same concept. The evidence table uses `service_request_id UUID NOT NULL REFERENCES cases(id)`.

## 3. Existing Evidence Capabilities

The evidence implementation lives in `internal/evidence/` and is **wired into the server** (`cmd/civora/main.go:107,201-202,259`).

### 3.1 Database Schema (migration 0003)

```sql
CREATE TABLE evidence (
    id                  UUID PRIMARY KEY,
    organization_id     UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    service_request_id  UUID NOT NULL REFERENCES cases(id) ON DELETE CASCADE,
    type                TEXT NOT NULL,
    description         TEXT NOT NULL,
    storage_reference   TEXT NOT NULL,
    uploaded_by         UUID NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT valid_evidence_type CHECK (
        type IN ('IDENTITY_DOCUMENT', 'PROOF_OF_RESIDENCE', 'REFERRAL',
                 'SUPPORTING_DOCUMENT', 'PHOTOGRADE', 'STAFF_NOTE')
    )
);
CREATE INDEX idx_evidence_org ON evidence (organization_id);
CREATE INDEX idx_evidence_service_request ON evidence (service_request_id);
```

### 3.2 Domain Model (`internal/evidence/domain/evidence.go`)

```go
type Evidence struct {
    ID               uuid.UUID
    OrganizationID   uuid.UUID
    ServiceRequestID uuid.UUID    // = case ID
    Type             EvidenceType // hardcoded enum
    Description      string
    StorageReference string      // URI validated to s3:// gs:// azureblob:// civora:// schemes
    UploadedBy       uuid.UUID
    CreatedAt        time.Time
}
```

`EvidenceType` constants: `IDENTITY_DOCUMENT`, `PROOF_OF_RESIDENCE`, `REFERRAL`, `SUPPORTING_DOCUMENT`, `PHOTOGRAPH`, `STAFF_NOTE` (hardcoded in both Go and DB CHECK constraint).

`NewEvidence()` performs domain validation:
- Description required, max 5000 chars.
- Storage reference required, max 500 chars.
- Storage reference must be a valid URI with scheme in {s3, gs, azureblob, civora}.
- Storage reference must not contain credentials, query params, or fragments.
- Storage reference must not contain `..` path segments (path traversal protection).
- Storage reference must not contain control characters.

**No verification status, no metadata, no verification history.**

### 3.3 Repository Interface (`internal/evidence/domain/repository.go`)

```go
type EvidenceRepository interface {
    DB() *sql.DB
    Save(ctx, e) error
    SaveTx(ctx, tx, e) error
    FindByID(ctx, orgID, id) (*Evidence, error)
    FindByServiceRequest(ctx, orgID, srID, limit, offset) ([]*Evidence, error)
    CountByServiceRequest(ctx, orgID, srID) (int, error)
    FindByOrganization(ctx, orgID, limit, offset) ([]*Evidence, error)
}
```

All read methods scope by `organization_id`. Postgres implementation in `infrastructure/postgres/evidence_repository.go`.

### 3.4 Application Service (`internal/evidence/application/service.go`)

`EvidenceService` provides three operations:
- **AddEvidence** — validates case exists and belongs to org (via `shared.CaseFinder`), case is not closed, actor belongs to org (via `shared.UserChecker`), creates evidence in a transaction, records `evidence.added` audit event. Returns `ErrCaseNotFound`, `ErrCaseClosed`, `ErrUserNotFound`, `ErrEvidenceInput`.
- **GetEvidence** — delegates to `FindByID`, returns `ErrEvidenceNotFound`.
- **ListEvidence** — paginated list by service request (case), with limit clamped to [1, 200].

**No update, no delete, no verification, no file upload/retrieval.**

Dependencies (injected at `main.go:201`):
- `evidenceRepo` (PostgresEvidenceRepository)
- `caseRepo` (CaseFinder — shared.CaseFinder interface)
- `domain.NewOrganizationUserChecker(userRepo)` (UserChecker)

Routes registered at `/api/v1/organizations/{orgId}/evidence`:

## 4. Case / Document / Domain Relationships

### Evidence ↔ Case
- Evidence belongs to a `case` (via `service_request_id → cases(id)`).
- `EvidenceService.AddEvidence` validates the case exists, belongs to the org, and is not closed.
- FK constraint: `ON DELETE CASCADE` — deleting a case cascades to its evidence.

### Evidence ↔ Forms
- Evidence is **distinct from form submissions**. No foreign key or link exists between `evidence` and `form_submissions`.
- The `AssembleFactsFromCase` function (in `internal/rules/application/case_integration.go:386`) assembles facts for the rules engine from `case` and `form` (submissions) but **does not include evidence facts**. This is a gap for 0.7 Stage 6.

### Evidence ↔ Rules
- The rules engine (`internal/rules/domain/engine.go`) is pure: evaluates a `RuleSet` against a `Facts` map using dot-separated paths and whitelisted operators.
- `CaseRuleIntegrationService.AssembleFactsFromCase` (lines 386–453) builds `facts["case"]` and `facts["form"]` but **no `facts["evidence"]`**.
- Rules can reference evidence facts via paths like `evidence.identity_document.verification_status` — but this data is **not currently assembled**.
- Rule assignments are scoped to workflow states (`workflow_state_rule_assignments`), evaluated on transitions (`OnTransition` observer in cases service).
- **Gap:** No evidence requirements model exists. Rules cannot currently express "evidence type X must be VERIFIED."

### Evidence ↔ Human Review
- `review_queue` table (migration 0027) has an `evidence_ids JSONB` column (migration 0028) — review entries can reference evidence IDs.
- `decisions` table (migration 0026) has an `evidence_ids JSONB` column — decisions can reference evidence IDs.
- `ReviewQueueEntry` struct (`internal/review_queue/domain/review.go`) has `EvidenceIDs []uuid.UUID`.
- `Decision` struct (`internal/decisions/domain/decision.go`) has `EvidenceIDs []uuid.UUID`.
- However, these are **passive references** — no mechanism exists to attach, verify, or assess evidence during review. The `CompleteReview` method passes `entry.EvidenceIDs` to `CreateDecisionTx` but does not validate evidence verification status.
- **Gap:** Human review does not assess evidence verification.

### Evidence ↔ Audit
- `evidence.added` and `evidence.deleted` actions are in the audit vocabulary (migrations 0007, 0008, 0018, 0020, 0025, 0031).
- `AddEvidence` records an `evidence.added` audit event with metadata `{service_request_id, evidence_type}`.
- **Gap:** No `evidence.verified`, `evidence.rejected`, `evidence.needs_review`, or `evidence.metadata_updated` audit actions exist in the vocabulary.

## 6. Missing Capabilities

The following capabilities required by CIVORA 0.7 are **absent** from the current codebase:

### Stage 2 — Evidence Domain (core model)
1. **No verification status field** — `Evidence` struct has no `verification_status` / `verification_state`.
2. **No verification information** — no `verifier_id`, `verified_at`, `verification_reason`, `verification_method`, `verification_notes`.
3. **No metadata field** — `Evidence` struct has no `Metadata` (JSONB) field.
4. **No verification history** — no audit trail of verification state transitions.
5. **No evidence source field** — no tracking of how evidence entered the system (upload, external reference, structured record).
6. **Hardcoded evidence types** — `EvidenceType` is a fixed Go enum + DB CHECK constraint. Not configurable per organization or workflow. Violates 0.7's "Do NOT hardcode specific documents/organizations" requirement.

### Stage 3 — File & Document Storage
7. **No file storage abstraction** — `storage_reference` is a URI string validated against a scheme whitelist. There is no upload endpoint, no download/retrieval endpoint, no local filesystem storage, no content-type/size/checksum validation on actual bytes.
8. **No local development storage** — the `civora://` scheme is accepted but no Go implementation exists for it.
9. **No object storage adapter** — the `s3://`/`gs://`/`azureblob://` schemes are accepted as URIs but there is no Go code that reads or writes actual objects. The storage reference is opaque to CIVORA.

### Stage 4 — Evidence API
10. **No file upload endpoint** — evidence is created by providing a pre-existing `storage_reference` URI. There is no multipart upload that stores bytes.
11. **No document download endpoint** — no way to retrieve an uploaded/verified document through CIVORA APIs.
12. **No evidence update endpoint** — metadata updates are not supported (though 0.7 requires "update permitted metadata" without weakening immutability of key fields).
13. **No evidence delete endpoint** — audit vocabulary has `evidence.deleted` but no API or service method exists to delete evidence.
14. **No verification API endpoints** — no verify, reject, or mark-for-review operations.

### Stage 5 — Evidence Verification
15. **No verification lifecycle** — no `VerifyEvidence`, `RejectEvidence`, `MarkForReview` service methods or domain logic.
16. **No verification history table** — no immutable record of who verified when and why.
17. **No verification permission model** — no concept of "reviewer" vs. "uploader" roles for evidence.

### Stage 6 — Evidence + Forms + Rules Integration
18. **No evidence requirements model** — no way to declare "identity document required" per workflow state, form, or rule set. The `WorkflowRequirements` struct (cases application) tracks form requirements only.
19. **No evidence facts in rule evaluation** — `AssembleFactsFromCase` does not assemble evidence data. Rules cannot reference `evidence.*` fact paths.
20. **No evidence in form submissions** — form submissions are separate from evidence; no linking mechanism exists (this is by design but means evidence requirements can't be form-driven without new integration).

### Stage 7 — Evidence Workspace Frontend
21. **Frontend evidence display is minimal** — `app.js:1199-1207` renders evidence type and description only. No verification state display, no verification history, no upload UI, no document download/open, no metadata display.
22. **No upload UI** — the evidence modal (`evidence-modal`) is referenced in `showSectionForm` but there is no file upload widget.
23. **No verification UI** — no buttons or flows for verifying/rejecting evidence in the review workspace.

### Stage 8 — Security (hostile review)
24. **No upload security** — no file size limits, no MIME type validation, no checksum verification, no filename sanitization (because no upload exists yet).
25. **No evidence-specific IDOR tests** — existing e2e tests cover cross-tenant read and unauthenticated access but not evidence ID substitution or document download IDOR.

## 7. Security Concerns

### Current Security Posture (0.6 evidence)
- **Tenant isolation:** Strong. `RequireSameTenant` middleware + org-scoped DB queries + `shared.CaseFinder`/`UserChecker` validation. E2e tests verify cross-tenant read is blocked (403).
- **Authorization:** Admin/staff roles enforced via `RequireAnyRole`.
- **Storage reference leakage:** Prevented — `serializeEvidence` omits `storage_reference` from API responses. E2e test verifies this.
- **Path traversal:** Storage reference validation rejects `..` segments and `file://` scheme.
- **Audit:** Hash-chained, schema-isolated. Evidence creation is audited (`evidence.added`).
- **IDOR:** `FindByID(ctx, orgID, id)` always scopes by org. Cross-tenant GetEvidence returns 404 (not 403) in the service layer; the e2e test checks 403 at the middleware level.

### Risks Introduced by 0.7 Work
1. **File upload attack surface** — adding upload/download will introduce: path traversal, MIME spoofing, oversized files, malicious filenames, cross-tenant retrieval, request-body exhaustion, storage path manipulation, direct filesystem access. These must be addressed proactively, not reactively.
2. **Hardcoded evidence types** — the DB CHECK constraint on `evidence.type` and the Go `EvidenceType` enum are not configurable. Stage 2 must decide whether to replace this with a configurable type system or extend it. Changing the CHECK constraint requires a new migration.
3. **Evidence ≠ verification conflation** — the existing model has no verification concept. Adding verification must not be confused with evidence existence or rule results. Clear state machine boundaries are required.
4. **`storage_reference` is currently opaque** — if 0.7 adds file upload, the storage reference will transition from a client-provided URI to a server-generated internal reference. The migration path must ensure old evidence with external URIs remains valid.
5. **Audit vocabulary expansion** — adding `evidence.verified`, `evidence.rejected`, `evidence.reopened` requires dropping and re-adding the `valid_audit_action` CHECK constraint (as every audit vocabulary migration does). This is the established pattern (migrations 0007, 0010, 0018, 0020, 0025, 0031).

### Security Gaps Requiring Attention in 0.7
- No file upload/download security controls exist yet (to be built in Stage 3).
- No reviewer-specific authorization (currently only admin/staff roles; verification may need a "can_verify_evidence" permission).
- No filename sanitization or content-type detection for uploads.
- No evidence deletion authorization (delete endpoint doesn't exist).

## 8. Data-Model Recommendations

### Recommendation 1: Add a verification status column to `evidence`
Add `verification_status TEXT NOT NULL DEFAULT 'UNVERIFIED'` with a CHECK constraint:
`CHECK (verification_status IN ('UNVERIFIED', 'NEEDS_REVIEW', 'VERIFIED', 'REJECTED'))`.

Add nullable columns: `verified_by UUID REFERENCES users(id)`, `verified_at TIMESTAMPTZ`, `verification_reason TEXT`, `verification_method TEXT`.

### Recommendation 2: Add a metadata column
Add `metadata JSONB DEFAULT '{}'::jsonb` to store arbitrary structured metadata (e.g., file size, content type, checksum, filename, person/entity reference). This follows the pattern already used by `review_queue.metadata`, `eligibilities.criteria`, etc.

### Recommendation 3: Add a verification history table
Create `evidence_verification_history` with columns: `id`, `evidence_id` (FK→evidence), `status`, `verifier_id` (FK→users), `verified_at`, `reason`, `method`, `notes`, `created_at`. Immutable — verification state changes are append-only.

### Recommendation 4: Add a storage/documents table
If 0.7 adds actual file upload (Stage 3), create an `evidence_documents` table (or `evidence_storage`) with: `id` (FK→evidence), `file_name`, `content_type`, `size_bytes`, `checksum`, `storage_key` (internal, never exposed), `uploaded_by`, `uploaded_at`. The `evidence.storage_reference` becomes a computed/derived pointer to this table.

### Recommendation 5: Consider configurable evidence types
The hardcoded `EvidenceType` enum (`IDENTITY_DOCUMENT`, `PROOF_OF_RESIDENCE`, etc.) violates 0.7's configurability requirement. Either:
- (a) Replace the hardcoded CHECK constraint with a free-text `evidence_type` column and let evidence types be configured per-organization (e.g., via the workflow or rule configuration), or
- (b) Keep a `evidence_type` TEXT column without a fixed CHECK, allowing runtime-configurable types.

This must be decided in Stage 2. The decision affects the migration and the domain model.

### Recommendation 6: Add indexes
- `idx_evidence_org_type` ON evidence (organization_id, type)
- `idx_evidence_org_verification` ON evidence (organization_id, verification_status)
- For verification history: `idx_evidence_verification_evidence_id` ON evidence_verification_history (evidence_id)

## 9. API Recommendations

### Recommendation 1: Add verification endpoints
Following the existing RESTful pattern:
```
POST /organizations/{orgId}/evidence/{evidenceId}/verify   — verify evidence
POST /organizations/{orgId}/evidence/{evidenceId}/reject   — reject evidence
POST /organizations/{orgId}/evidence/{evidenceId}/review   — mark for review
GET  /organizations/{orgId}/evidence/{evidenceId}/history   — list verification history
GET  /organizations/{orgId}/evidence/{evidenceId}/document — download/retrieve document (if file upload is added)
```

### Recommendation 2: Add metadata to evidence API
Include `metadata` in the CreateEvidenceRequest and Evidence response schema. Allow updating only permitted metadata fields.

### Recommendation 3: Keep storage_reference internal
If file upload is added, the API should return a server-controlled download URL (signed or proxied), never the raw storage path. The existing `serializeEvidence` already omits `storage_reference` — extend this principle to any internal storage keys.

### Recommendation 4: Add verification authorization
Introduce a permission check beyond admin/staff for verification operations. Consider a `reviewer` role or a `can_verify_evidence` capability. Alternatively, gate verification on `RequireAnyRole("admin", "staff")` with the additional constraint that the actor must not be the evidence uploader (to maintain separation of duties).

### Recommendation 5: Update OpenAPI spec
Add new endpoints and schema extensions to `api/openapi/openapi.yaml`. Update the `Evidence` schema to include `verification_status`, `metadata`, `verified_by`, `verified_at`. Add `VerificationHistory` schema.

## 10. Frontend Recommendations

### Gap Analysis of `web/js/app.js`
- Evidence is rendered in `loadSection('evidence', ...)` (line 1136) and in the review workspace (lines 757–768).
- Current evidence rendering shows only `type` and `description` as a table.
- No upload UI exists (the `evidence-modal` is referenced but not inspected for upload capability).
- No verification state display, no verification buttons, no history view.
- `escapeHTML` is used for all evidence data rendering (security-correct).

### Recommendations for Stage 7
1. **Evidence workspace section** — render verification status as a badge, show verification history, show metadata.
2. **Upload UI** — a modal with file input, filename display, size, and a "Upload" button that POSTs to a new upload endpoint. Enforce client-side size limits (but not rely on them — server must enforce).
3. **Verification UI** — "Verify" / "Reject" / "Mark for Review" buttons in the reviewer workspace, with a reason/notes text input. Gate these on the user's role.
4. **Document download** — a "Download" / "Open" link that fetches from the document retrieval endpoint with authorization.
5. **Distinguish verification from rule result and human decision** — use separate badge colors and labels as the task requires.
6. **Never expose internal storage paths** — URLs should be API endpoints, not raw storage paths.
7. **Handle edge cases** — empty evidence, missing evidence, upload failure, unauthorized access, oversized file, invalid file, loading states, stale state, concurrent changes.

### Configurability
- Evidence types should be rendered from backend configuration, not hardcoded in frontend.
- The section-to-transition mapping (`buildSectionTransitionMap`, line 1061) currently infers evidence section relevance from transition key/name keywords — this is a reasonable configurable approach and should be preserved.
