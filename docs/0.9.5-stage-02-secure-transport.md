## 1. Executive Summary

Stage 1 verified that **H3 (TLS)** is a confirmed 1.0 blocker: CIVORA shipped
with no TLS termination, dead-code HSTS, and all documented deployments
exposing plain HTTP. This stage resolves the blocker by implementing a
defensible transport-security architecture that supports both reverse-proxy
and direct TLS termination, without forcing all deployments into application-
level TLS.

**Outcome**: H3 blocker resolved. No documented production deployment exposes
plain HTTP to the Internet.

**Review Status**: Approved — implementation verified against Stage 02 requirements.
All tests pass (`go test ./internal/middleware/... ./internal/server/...`), build
and vet clean, and gofmt clean. No security issues identified in the trusted
proxy boundary, HSTS emission logic, or forwarded-header handling.

## 2. Architecture

### 2.1 Deployment Models

CIVORA supports two transport-security models. Operators choose one; both are
equally valid.

#### Model A — Reverse-Proxy TLS Termination (Recommended)

```
Internet
  ↓  HTTPS (TLS 1.2+)
Reverse Proxy (Caddy / nginx / load balancer)
  ↓  HTTP (plain, internal network)
CIVORA
```

- The reverse proxy is the only publicly reachable component.
- CIVORA listens on plain HTTP internally.
- The proxy sets `X-Forwarded-Proto: https` and `X-Forwarded-For`.
- CIVORA trusts these headers only from explicitly configured proxy IPs.

**When to use**: Production, cloud, multi-instance, any environment where a
reverse proxy is already present or where automatic certificate management
(Let's Encrypt) is desired.

#### Model B — Direct TLS Termination

```
Internet
  ↓  HTTPS (TLS 1.2+)
CIVORA (Go TLS listener)
```

- CIVORA loads a certificate and private key from disk.
- `http.Server.ServeTLS` handles TLS termination.
- HSTS is emitted automatically because `r.TLS != nil` is true.

**When to use**: Single-instance deployments, edge devices, environments
without a separate proxy layer.

### 2.2 Trust Boundary

```
┌─────────────────────────────────────────────────────┐
│  Internet (Untrusted)                               │
│                                                     │
│  ┌───────────────────────────────────────────────┐  │
│  │  Reverse Proxy / Load Balancer                 │  │
│  │  ───────────────────────────────────────────  │  │
│  │  Terminates TLS. Sets X-Forwarded-* headers.   │  │
│  │  IP is listed in CIVORA_SERVER_TRUSTED_PROXIES │  │
│  └───────────────────────────────────────────────┘  │
│                    │                                 │
│          Trust boundary: proxy → CIVORA              │
│                    ↓                                 │
│  ┌───────────────────────────────────────────────┐  │
│  │  CIVORA                                       │  │
│  │  ───────────────────────────────────────────  │  │
│  │  - ProxyHeaders middleware validates peer IP   │  │
│  │  - Only trusted proxies may set X-Forwarded-* │  │
│  │  - HSTS emitted only for actual HTTPS          │  │
│  │  - Direct TLS available via cert/key env vars  │  │
│  └───────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────┘
```

**Rule**: `X-Forwarded-*` headers from any IP not listed in
`CIVORA_SERVER_TRUSTED_PROXIES` are ignored. If the list is empty, all
forwarded headers are ignored and client identity is taken from the direct
TCP peer.

## 3. Configuration

### 3.1 Environment Variables

| Variable | Default | Description |
|----------|---------|-------------|
| `CIVORA_SERVER_PORT` | `8080` | Listen port. Ignored when TLS cert/key are set (still used for TLS listener). |
| `CIVORA_SERVER_TLS_CERT` | `""` | Path to PEM certificate file for direct TLS. When set, `CIVORA_SERVER_TLS_KEY` must also be set. |
| `CIVORA_SERVER_TLS_KEY` | `""` | Path to PEM private key file for direct TLS. |
| `CIVORA_SERVER_TRUSTED_PROXIES` | `""` | Comma-separated list of proxy IPs or CIDRs (e.g., `10.0.0.1,10.0.0.0/24`). **Required** when `CIVORA_SERVER_FORCE_HTTPS=true`. |
| `CIVORA_SERVER_FORCE_HTTPS` | `false` | When `true`, CIVORA trusts `X-Forwarded-Proto: https` from trusted proxies and emits HSTS. |

### 3.2 Startup Validation

The configuration loader enforces the following invariants at startup:

1. `CIVORA_SERVER_TLS_CERT` and `CIVORA_SERVER_TLS_KEY` must both be set or
   both be empty.
2. `CIVORA_SERVER_FORCE_HTTPS=true` requires `CIVORA_SERVER_TRUSTED_PROXIES`
   to be non-empty.

If validation fails, CIVORA exits with a descriptive error before accepting
any requests.

### 3.3 HSTS Emission Rules

HSTS is emitted **only** when the deployment is actually HTTPS:

| Condition | HSTS Header |
|-----------|-------------|
| Direct TLS (`TLSCertFile` + `TLSKeyFile` set) | `max-age=31536000; includeSubDomains` |
| `FORCE_HTTPS=true` + request from trusted proxy + `X-Forwarded-Proto: https` | `max-age=31536000; includeSubDomains` |
| Plain HTTP development (no TLS, no proxy) | **Not emitted** |
| `FORCE_HTTPS=true` but request from untrusted source | **Not emitted** |

## 4. Middleware Stack

### 4.1 `ProxyHeaders`

```go
r.Use(middleware.ProxyHeaders(cfg.Server.TrustedProxies))
```

- Validates that the immediate TCP peer is in `TrustedProxies`.
- If trusted, reads `X-Forwarded-Proto` (must be `https` or `http`) and sets
  `r.URL.Scheme`.
- Does **not** modify `r.RemoteAddr`; downstream code uses `RealIP` for
  client identity.

### 4.2 `SecureHeaders`

```go
r.Use(middleware.SecureHeaders(func(r *http.Request) bool {
    return r.TLS != nil || (cfg.Server.ForceHTTPS && isFromTrustedProxy(r) && r.Header.Get("X-Forwarded-Proto") == "https")
}))
```

Sets the following headers on every response:

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `X-XSS-Protection: 1; mode=block`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'`
- `Cache-Control: no-store, no-cache, must-revalidate`
- `Strict-Transport-Security: max-age=31536000; includeSubDomains` (conditionally)

### 4.3 `RealIP` (rate limiting + logging)

```go
ip := middleware.RealIP(r, trustedProxies)
```

Returns the best available client IP:
1. If the direct peer is a trusted proxy, returns the first valid IP from
   `X-Forwarded-For`.
2. Otherwise, returns the direct TCP remote address.

Malformed IPs in headers are silently skipped; the function falls back to the
direct peer.

## 5. Implementation Details

### 5.1 Direct TLS in `internal/server/server.go`

```go
func (s *Server) Start(ctx context.Context) error {
    // ...
    if s.cfg.Server.TLSKeyFile != "" && s.cfg.Server.TLSCertFile != "" {
        return s.httpServer.ServeTLS(listener, s.cfg.Server.TLSCertFile, s.cfg.Server.TLSKeyFile)
    }
    return s.httpServer.Serve(listener)
}
```

When both `TLSCertFile` and `TLSKeyFile` are configured, the server uses
`ServeTLS` on the existing TCP listener. No separate port or listener is
created; the same port serves HTTPS.

### 5.2 HTTPS Detection in `SecureHeaders`

```go
func isFromTrustedProxy(r *http.Request, trustedProxies []string) bool {
    return middleware.IsTrustedProxy(middleware.RemoteHost(r.RemoteAddr), trustedProxies)
}
```

Combined with `ForceHTTPS`, this ensures HSTS is only emitted when the
request actually arrived over HTTPS through a verified proxy.

## 6. Production Deployment Example

### 6.1 Caddy Reverse Proxy

Create a `Caddyfile` in the same directory as `docker-compose.yml`:

```text
civora.example.com {
    reverse_proxy app:8080 {
        header_up X-Forwarded-For {remote_host}
        header_up X-Forwarded-Proto {scheme}
        header_up X-Real-IP {remote_host}
    }
}
```

Caddy automatically:
- Obtains and renews TLS certificates via Let's Encrypt.
- Redirects HTTP → HTTPS.
- Sets `X-Forwarded-Proto` to `https` on every proxied request.

Set the following environment variables for the CIVORA container:

```bash
CIVORA_SERVER_TRUSTED_PROXIES=10.0.0.0/8   # Caddy's internal network CIDR
CIVORA_SERVER_FORCE_HTTPS=true
```

### 6.2 nginx Reverse Proxy

```nginx
server {
    listen 80;
    server_name civora.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name civora.example.com;

    ssl_certificate     /etc/letsencrypt/live/civora.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/civora.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;

    location / {
        proxy_pass         http://app:8080;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
    }
}
```

Set the same `CIVORA_SERVER_TRUSTED_PROXIES` and `CIVORA_SERVER_FORCE_HTTPS`
environment variables.

### 6.3 Docker Compose (Production Skeleton)

```yaml
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: ${CIVORA_DB_USER:-civora}
      POSTGRES_PASSWORD: ${CIVORA_DB_PASSWORD}
      POSTGRES_DB: ${CIVORA_DB_NAME:-civora}
    volumes:
      - pg_data:/var/lib/postgresql/data
    restart: unless-stopped

  app:
    build: .
    depends_on:
      db:
        condition: service_healthy
    environment:
      CIVORA_SERVER_PORT: 8080
      CIVORA_DB_HOST: db
      CIVORA_DB_PORT: 5432
      CIVORA_DB_USER: ${CIVORA_DB_USER:-civora}
      CIVORA_DB_PASSWORD: ${CIVORA_DB_PASSWORD}
      CIVORA_DB_NAME: ${CIVORA_DB_NAME:-civora}
      CIVORA_DB_SSLMODE: require
      CIVORA_AUTH_JWT_SECRET: ${CIVORA_AUTH_JWT_SECRET}
      CIVORA_SERVER_TRUSTED_PROXIES: 10.0.0.0/8
      CIVORA_SERVER_FORCE_HTTPS: "true"
    restart: unless-stopped
    # Do NOT publish port 8080 to the Internet.
    # Only the reverse proxy should reach the app container.

  caddy:
    image: caddy:2-alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    depends_on:
      - app
    restart: unless-stopped

volumes:
  pg_data:
  caddy_data:
  caddy_config:
```

**Critical**: Do not add `ports: - "8080:8080"` to the `app` service in
production. The app container's HTTP port must be reachable only by the
reverse proxy on the internal Docker network.

## 7. HTTP-to-HTTPS Deployment Guidance

### 7.1 With Reverse Proxy (Recommended)

The reverse proxy handles the HTTP→HTTPS redirect. CIVORA never receives
plain HTTP from the Internet.

**Caddy**: Automatic — `reverse_proxy` implies HTTPS redirect.
**nginx**: Explicit `return 301 https://$host$request_uri;` on port 80.

### 7.2 With Direct TLS

If CIVORA terminates TLS directly and you also want to redirect port 80→443,
run a second listener or a tiny redirect sidecar:

```go
// In main.go (optional redirect listener)
go func() {
    redirect := &http.Server{
        Addr: ":80",
        Handler: http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            target := "https://" + r.Host + r.URL.RequestURI()
            http.Redirect(w, r, target, http.StatusMovedPermanently)
        }),
    }
    log.Fatal(redirect.ListenAndServe())
}()
```

Or use iptables / firewall rules to redirect port 80 to 443 at the OS level.

## 8. Threat Model Updates

### T-13a: TLS Misconfiguration or Absence (NEW)

**Description**: CIVORA is deployed without TLS, exposing all traffic
(including JWTs and sensitive case data) to passive interception or
man-in-the-middle attacks. Alternatively, a misconfigured reverse proxy
leaks `X-Forwarded-*` headers from untrusted clients, allowing IP spoofing
or HSTS bypass.

**Affected assets**: All in-transit data.

**Mitigation strategies**:
- CIVORA supports direct TLS termination via `CIVORA_SERVER_TLS_CERT` /
  `CIVORA_SERVER_TLS_KEY`.
- Reverse-proxy deployments must set `CIVORA_SERVER_TRUSTED_PROXIES` to
  the proxy's IP/CIDR.
- `CIVORA_SERVER_FORCE_HTTPS` enables HSTS emission when behind a trusted
  proxy.
- Forwarded headers are only trusted from explicitly configured proxy IPs.
- Plain HTTP must not be exposed directly to the Internet.

**Severity**: High

### T-13: Insecure Configuration (UPDATED)

**Added**:
- TLS is supported via direct cert/key files or reverse-proxy headers; HSTS
  is emitted only when the deployment is actually HTTPS.
- `CIVORA_SERVER_FORCE_HTTPS` requires `CIVORA_SERVER_TRUSTED_PROXIES` to
  be configured, preventing accidental HSTS on plain HTTP.

### T-08: Data Leakage (UPDATED)

**Added**: TLS in transit is now implemented and configurable; encryption at
rest remains a post-1.0 item.

The client (browser) sees this over HTTPS because the proxy terminates TLS.

## 11. Security Guarantees

1. **No plain HTTP to Internet**: Documented production deployments always
   place a reverse proxy in front of CIVORA. The Docker Compose production
   skeleton does not publish the app port externally.
2. **Forwarded headers are untrusted by default**: If `CIVORA_SERVER_TRUSTED_PROXIES`
   is empty, `X-Forwarded-For`, `X-Real-IP`, and `X-Forwarded-Proto` are
   ignored.
3. **HSTS is never emitted on development HTTP**: HSTS requires either direct
   TLS or an explicit `ForceHTTPS` + trusted proxy configuration.
4. **Malformed proxy headers are rejected**: `RealIP`, `ProxyHeaders`, and
   `IsTrustedProxy` all use `net.ParseIP` and fall back to the direct peer
   when headers contain invalid values.
5. **Startup validation**: Misconfigured TLS or proxy settings cause the
   server to fail at startup rather than running in an insecure state.

## 12. Open Items (Post-1.0)

| Item | Rationale |
|------|-----------|
| Automatic HTTP→HTTPS redirect when direct TLS is enabled | Not required for 1.0; operators can use a sidecar redirect or OS-level rules. |
| Per-organization or per-user TLS certificate support | Not required for 1.0; single cert/key per instance is sufficient. |
| OCSP stapling for direct TLS | Post-1.0 enhancement; Go's `crypto/tls` supports it but it is not enabled here. |
| `Permissions-Policy` header | Add when frontend requirements are finalized. |
