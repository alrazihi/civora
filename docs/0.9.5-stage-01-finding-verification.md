## C1 — JWT Token Lifecycle

### Original Severity: HIGH

### Verification Result: CONFIRMED

### Evidence

| Aspect | Finding | File:Line |
|--------|---------|-----------|
| Token lifetime | 24h default, configurable via `CIVORA_AUTH_JWT_EXPIRY` | `internal/config/config.go:101` |
| Token generation | JWT bakes `sub`, `organization_id`, `role`, `iss`, `iat`, `exp`, `jti` | `internal/middleware/auth.go:39-55` |
| Refresh tokens | **None exist** — no refresh token generation, validation, rotation, or storage | Full codebase search: zero matches |
| Revocation | **None exist** — `jti` generated but never stored or checked; no blacklist, no session table | `internal/middleware/auth.go:50` |
| Logout | **No server-side logout endpoint** — only client-side `app.logout()` in frontend | `internal/identity/api/handler.go:46-57` |
| Password change | **No password change endpoint** — `UserRepository` has no `Update` method | `internal/identity/domain/repository.go` |
| Credential change | **No user update endpoints** — email/role cannot be changed via API | `internal/identity/api/handler.go` |
| Role changes | Role is baked into JWT at login; `RequireAnyRole` checks static claim, not DB | `internal/identity/application/service.go:196-204` |
| Token theft | Stolen token is valid for up to 24h with no kill switch, no IP binding | `internal/middleware/auth.go:93-120` |
| TLS | **No TLS** — plain `http.Server` with TCP listener; HSTS conditional on `r.TLS != nil` (never true) | `internal/server/server.go:54-62`, `internal/middleware/headers.go:15-17` |

### Actual Impact

- **Authentication replay**: A stolen JWT grants full access for up to 24 hours with no revocation mechanism.
- **Privilege escalation delay**: Role changes take effect only after token expiry (up to 24h).
- **No logout semantics**: Server cannot invalidate tokens; logout is cosmetic.
- **No credential invalidation**: Password/email changes cannot invalidate existing tokens.

### Exploitability

**HIGH** — Token theft is straightforward (XSS, logging, client compromise). No additional attack complexity required.

### Required Remediation

1. Implement short-lived access tokens (15-30 min) + refresh tokens (days) with rotation
2. Add `sessions` table with `jti`, `refresh_token_hash`, `expires_at`, `revoked_at`
3. Implement `POST /auth/logout` that revokes current token and all refresh tokens
4. Add password change endpoint that revokes all active sessions
5. Re-resolve role from DB on each request or use sufficiently short tokens
6. Enable TLS termination (reverse proxy or `ListenAndServeTLS`)
7. Add key rotation support (`kid` header)

### Whether it blocks 1.0: **YES**

### Recommended 1.0 Treatment

**BLOCKER** — The 24h static JWT with no revocation, no refresh tokens, and no TLS is insufficient for a case-management system handling sensitive service-delivery data. Minimum 1.0 architecture requires:
- TLS termination
- Short-lived tokens with refresh/rotation
- Server-side revocation capability
- Logout semantics

## C2 — Audit Tamper Resistance

### Original Severity: CRITICAL

### Verification Result: CONFIRMED (with nuance)

### Evidence

| Attacker Profile | Can Modify/Erase | Evidence |
|------------------|------------------|----------|
| Normal application privileges | **No** (through API) | Audit API is read-only for admin/staff roles |
| Organization-admin privileges | **No** (through API) | Same as above; no admin-only mutation endpoints |
| Application-server access | **YES** | App DB user has full DML on `audit.audit_events`; no separate read-only user |
| Database-write access | **YES** | Any principal with INSERT/UPDATE/DELETE on audit table can modify rows |
| Full database-admin access | **YES** | Can DROP SCHEMA, TRUNCATE, modify constraints, disable triggers |

### Hash Chain Detection Analysis

| Attack | Detected? | Mechanism | Gap |
|--------|-----------|-----------|-----|
| Deletion (interior) | **Yes** | `PreviousHash` mismatch in `VerifyChain` | — |
| Deletion (trailing) | **No** | Last surviving event has no successor to complain | `internal/audit/domain/event.go:127-152` |
| Insertion (no recompute) | **Yes** | `PreviousHash` mismatch | — |
| Insertion (with recompute) | **No** | Attacker can recompute all hashes consistently | No external anchor |
| Modification | **Yes** | `VerifyIntegrity()` detects hash mismatch | — |
| Reordering (no recompute) | **Yes** | `PreviousHash` points to wrong predecessor | — |
| Reordering (with recompute) | **No** | Attacker can recompute hashes after reordering | No external anchor |
| Chain recomputation | **No** | Entirely self-referential; no external anchor | `docs/audit-integrity.md:91-98` |

### Real Requirement Classification

| Requirement | Status | Evidence |
|-------------|--------|----------|
| Application tamper evidence | **Provided** | Hash chain detects accidental/offline modification |
| Append-only storage | **Not provided** | No DB-level INSERT-only restriction |
| WORM archive | **Not provided** | No external WORM storage |
| External anchoring | **Not provided** | No blockchain, timestamp authority, or external witness |
| Detection against DB compromise | **Not provided** | Documented limitation in `docs/audit-integrity.md:94-98` |

### Actual Impact

The hash chain provides **tamper evidence against accidental corruption and casual/offline tampering**, not against a malicious database administrator. This is honestly documented.

### Exploitability

**MEDIUM** — Requires database-level access, which is a high bar. The application itself does not expose audit mutation.

### Whether it blocks 1.0: **NO** (documented limitation)

### Recommended 1.0 Treatment

**DOCUMENTATION FIX** — The documentation already correctly describes these limitations. No code change required before 1.0 if the threat model accepts that DB admins are trusted. If regulatory requirements demand stronger guarantees, add:
- Database-level append-only triggers or RLS policies
- External anchoring (e.g., periodic hash export to external storage)
- Separate read-only database user for application

## H1 — Database Compromise

### Original Severity: HIGH

### Verification Result: CONFIRMED

### Evidence

| Finding | Status | Detail | File:Line |
|---------|--------|--------|-----------|
| Password hashing | **OK** | bcrypt with cost 12 (min 10 enforced) | `internal/identity/domain/user.go:62-68`, `internal/config/config.go:102` |
| Encryption at rest | **FAIL** | No application-level encryption; all PII stored as plaintext in PostgreSQL | Full codebase search: zero `encrypt` matches |
| PII storage | **FAIL** | Names, emails, phones, addresses, DOB, form data stored unencrypted | `internal/people/domain/person.go:23-38`, `internal/form_submission/domain/submission.go:34-45` |
| Evidence storage | **PARTIAL** | Plaintext files on local filesystem; path traversal prevented but no encryption | `internal/evidence/infrastructure/storage/local_provider.go:27-42` |
| Backup exposure | **OPERATOR** | No backup code exists; operator responsibility per README | `README.md:442-456` |
| Secrets | **PARTIAL** | JWT secret min 32 chars; DB credentials default to `civora`/`civora`; `.env` on disk | `internal/config/config.go:90-130`, `.env.example` |
| Database access | **PARTIAL** | Single DB user with full DML on all schemas; SSL disabled by default | `docker-compose.yml:34-35`, `internal/config/config.go:94-97` |

### Actual Impact

- **Offline attack risk**: If PostgreSQL data files are stolen, all PII and password hashes are immediately accessible. bcrypt cost 12 makes password cracking slow but not impossible for targeted attacks.
- **Database admin risk**: A PostgreSQL superuser can read all data, modify audit logs, and bypass all application-level controls.
- **Evidence files**: Local filesystem storage with no encryption means physical disk access exposes all uploaded documents.

### Exploitability

**MEDIUM** — Requires physical disk access or database compromise, which is a high bar. Not remotely exploitable without prior compromise.

### Whether it blocks 1.0: **NO** (documentation/operator responsibility)

### Recommended 1.0 Treatment

**ARCHITECTURAL FIX (post-1.0)** — Encryption at rest, separate read-only DB user, and external evidence storage are post-1.0 items. Before 1.0:
1. **Document** that encryption at rest is NOT implemented and is operator responsibility
2. **Document** that backup/DR is operator responsibility
3. **Change** default DB credentials and SSL mode in documentation
4. **Add** startup warnings when `sslmode=disable` in production-like environments

## H2 — Rate Limiting

### Original Severity: MEDIUM

### Verification Result: CONFIRMED

### Evidence

| Aspect | Status | Detail | File:Line |
|--------|--------|--------|-----------|
| Per-account (login) | **OK** | 20 failed attempts per 5min per email; 5min lockout | `internal/middleware/ratelimit.go:155-269`, `cmd/civora/main.go:218` |
| Per-account (registration) | **OK** | Same `UserRateLimiter` applied to registration | `internal/identity/api/handler.go:77-97` |
| Per-IP | **PARTIAL** | Token-bucket: 1000 req/s default, 200 burst; respects `X-Forwarded-For` from trusted proxies | `internal/middleware/ratelimit.go:77-101`, `internal/config/config.go:87-88` |
| Per-instance | **FAIL** | In-memory maps; state lost on restart | `internal/middleware/ratelimit.go:17-27` |
| Multi-instance | **FAIL** | No distributed store (Redis, etc.); each instance enforces independently | Full codebase search: zero distributed rate-limit matches |
| Login enumeration | **FAIL** | Different status codes for valid vs invalid accounts (401 vs 404) | `internal/identity/api/handler.go:268-285` |
| Distributed attacks | **FAIL** | Per-IP limits are per-instance; botnet rotates IPs across instances | — |
| Password reset | **N/A** | No password reset endpoint exists | Full codebase search: zero matches |

### Actual Impact

- **Login enumeration**: Attacker can confirm registered accounts by observing whether lockout triggers.
- **Distributed bypass**: Multi-instance deployments have no global rate limit; attackers distribute across instances.
- **No password reset**: Users who forget passwords require manual operator intervention.

### Exploitability

**MEDIUM** — Login enumeration is trivial. Distributed rate limit bypass requires modest resources.

### Whether it blocks 1.0: **NO** (but login enumeration is a security gap)

### Recommended 1.0 Treatment

1. **Fix login enumeration**: Return same status code (401) for both invalid credentials and non-existent users
2. **Add distributed rate limiting**: Redis-backed store or database-backed throttle for multi-instance deployments
3. **Add password reset endpoint**: Email-based or admin-assisted recovery
4. **Reduce default per-IP limit**: 1000 req/s is very permissive; consider 100-200 req/s default

## H3 — TLS

### Original Severity: HIGH

### Verification Result: CONFIRMED

### Evidence

| Aspect | Status | Detail | File:Line |
|--------|--------|--------|-----------|
| TLS termination | **None** | Plain `http.Server` with `net.Listen("tcp", addr)` | `internal/server/server.go:54-62` |
| Reverse proxy docs | **Partial** | `README.md` describes `localhost:8080`; no explicit reverse-proxy TLS guidance | `README.md:44` |
| HTTP exposure | **Possible** | No enforcement of HTTPS; all documented deployments use HTTP | `docker-compose.yml:41`, `.env.example` |
| HSTS | **Dead code** | Set only if `r.TLS != nil`, which is never true | `internal/middleware/headers.go:15-17` |
| Secure cookies | **N/A** | No cookies used; JWT in Authorization header | — |
| Deployment examples | **HTTP only** | Dockerfile exposes 8080; docker-compose maps 8080:8080 | `Dockerfile:22`, `docker-compose.yml:41` |

### Actual Impact

All traffic, including JWTs and sensitive case data, travels in plaintext by default. This enables:
- Passive network interception of JWTs
- Man-in-the-middle attacks
- Credential theft on untrusted networks

### Exploitability

**HIGH** — Trivial on untrusted networks; no additional attack complexity.

### Whether it blocks 1.0: **YES**

### Recommended 1.0 Treatment

**BLOCKER** — CIVORA must not ship without explicit TLS support. Minimum requirements:
1. Document that TLS termination is operator responsibility (reverse proxy)
2. Add `Strict-Transport-Security` unconditionally
3. Add `CIVORA_SERVER_TLS_CERT` / `CIVORA_SERVER_TLS_KEY` env vars for direct TLS
4. Reject `CIVORA_SERVER_TRUSTED_PROXIES` misconfiguration in production
5. Update all deployment examples to use HTTPS

## M1 — Case Status

### Original Severity: MEDIUM

### Verification Result: PARTIALLY CONFIRMED

### Evidence

| Code Path | Can Create Divergence? | Detail |
|-----------|------------------------|--------|
| API endpoints | **No** | `ChangeStatus` calls `changeStatusViaWorkflow`, which reloads case after transition and syncs status |
| Transactions | **No** | Case creation and workflow instance creation happen in same transaction; status synced from `instance.CurrentState` |
| Concurrent updates | **No** | Workflow transitions use optimistic locking (`version` check); case updates use same |
| Direct service calls | **No** | All status changes go through `SyncStatusFromWorkflow` or `ChangeStatus` |
| Workflow transitions | **No** | `ExecuteTransition` updates workflow instance state; case status is derived, not independently set |
| Case updates | **No** | `Case.Status` is denormalized mirror; `ValidateConsistency` checks agreement |
| Migrations | **No** | Migration 0012 adds CHECK constraints: `workflow_instance_id IS NULL OR workflow_state IS NOT NULL` |

**Key code references:**
- `internal/cases/domain/case.go:144-156` — `ValidateConsistency` returns `ErrCaseStatusContradiction` when status != workflow_state
- `internal/cases/application/service.go:269-280` — After workflow transition, `c.WorkflowState = instance.CurrentState` and `c.SyncStatusFromWorkflow(...)` are called
- `migrations/0012_case_workflow_constraints.up.sql:22-24` — CHECK constraint enforces consistency

### Actual Impact

The DB-level CHECK constraint and application-level `SyncStatusFromWorkflow` make divergence via supported code paths impossible. However, a direct SQL update could bypass application logic.

### Exploitability

**LOW** — Requires direct database access, which is already a full compromise scenario.

### Whether it blocks 1.0: **NO**

### Recommended 1.0 Treatment

**DOCUMENTATION FIX** — Document that `Case.Status` is a denormalized mirror of `WorkflowInstance.CurrentState` and that the CHECK constraint enforces consistency at the DB level. No code change required.

## M2 — AI Audit

### Original Severity: MEDIUM

### Verification Result: CONFIRMED (no gap)

### Evidence

All AI mutation paths use `withTx` → `database.InTransaction` and record audit events inside the same transaction:

| Method | Transaction | Audit Event | Domain Write |
|--------|-------------|-------------|--------------|
| `GenerateObservations` | `withTx` (line 272) | `ai.observations_generated` + per-observation `ai.observation.created` | `s.repo.SaveTx` (line 341) |

**Exception**: `recordAudit` (line 571-584) is called outside transactions on provider failure, but that path performs no domain mutation.

### Actual Impact

No AI mutation can commit without its audit event when audit is enabled. The provider-failure path silently drops audit errors but performs no domain writes.

### Exploitability

**NONE** — No gap exists in production paths.

### Whether it blocks 1.0: **NO**

### Recommended 1.0 Treatment

**REGRESSION TEST** — Add integration test that verifies rollback when audit write fails in AI mutation paths. Also fix silent error swallowing in `recordAudit` (line 575) to at least log the error.

## M3 — Idempotency

### Original Severity: MEDIUM

### Verification Result: PARTIALLY CONFIRMED

### Evidence

| Operation | Replay Protected? | Mechanism |
|-----------|-------------------|-----------|
| Decision (initial) | **Yes** | Duplicate check on `service_request_id` |
| Decision (supersede) | **NO** | No check for existing supersession; can create infinite chain |
| Workflow transition | **Yes** | State machine + optimistic locking (`version` check) |
| Form submission | **Yes** | Unique constraint on `(case_id, form_version_id)` via `SELECT FOR UPDATE` |
| Evidence verification | **NO** | No check for current `VerificationStatus`; status blindly overwritten |

**Additional finding**: `SupersedeDecision` is **broken in production** because:
1. Migration 0006 creates a unique index on `(organization_id, service_request_id)` for `decisions`
2. `SupersedeDecision` inserts a new row, which violates the unique index when a prior decision exists
3. `NewSupersedingDecision` sets `SupersededByID` to the new decision's own ID, not the previous decision's ID

### Actual Impact

- Evidence verification can be replayed to overwrite status and create duplicate history entries
- Supersede decision is broken in production due to DB constraint + domain logic bug

### Exploitability

**LOW** — Evidence verification replay requires authenticated access; the impact is limited to verification state confusion.

### Whether it blocks 1.0: **NO** (but evidence verification gap should be fixed)

### Recommended 1.0 Treatment

1. **Fix `SupersedeDecision`** — Either remove the unique index (if versioning is intended) or change to update-in-place
2. **Fix evidence verification** — Check current `VerificationStatus` before allowing state change
3. **No additional idempotency layer needed** — Existing state-machine and DB constraints adequately prevent duplicate effects for workflow transitions and form submissions

### Original Severity: MEDIUM

### Verification Result: NOT REPRODUCIBLE

### Evidence

| Attack Vector | Status | Detail |
|---------------|--------|--------|
| Guessed storage key via API | **Blocked** | `StorageKey` is `json:"-"`; never returned in API responses |
| Direct filesystem access via HTTP | **Blocked** | Evidence storage root is never mounted as HTTP file server |

### Actual Impact

No vulnerability exists. The previous finding assumed predictable storage keys could bypass authorization, but the API layer never exposes storage keys and always validates tenant membership before retrieval.

### Exploitability

**NONE** — No attack path exists.

### Whether it blocks 1.0: **NO**

### Recommended 1.0 Treatment

**FALSE POSITIVE** — No code change required. Document that evidence storage authorization is enforced at the API/service layer, not the storage provider layer.
