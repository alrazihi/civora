## 3. Current Architecture Verification

### 3.1 Workflow Architecture

The workflow engine is a first-class, configurable state machine:

- **Workflow Definition** — versioned, tenant-scoped template with states, transitions, metadata. Statuses: `DRAFT`, `ACTIVE`, `ARCHIVED`.
- **Workflow Instance** — execution of a definition for a specific case. Retains definition/version.
- **Workflow Transition History** — immutable record of every transition with actor, reason, metadata, and optional `decision_id` linkage.
- **Authorization** — transitions can declare `allowed_roles`; workflow service checks actor's role.
- **Concurrency** — optimistic concurrency control via `version` column on instances.
- **Audit** — every transition creates an audit event (`workflow.transition`).

**Key property:** The `Case` table stores `workflow_instance_id` as a foreign key. `Case.Status` is a denormalized mirror of `WorkflowInstance.CurrentState`. All state changes go through `WorkflowService.ExecuteTransition`.

### 3.2 Cases

- `Case` entity with `ID`, `OrganizationID`, `CaseNumber`, `Status`, `ServiceType`, `Priority`, `WorkflowInstanceID`, `WorkflowState`, `ClosedAt`, `Version`.
- `CaseStatistics` struct with totals, breakdowns by status/service_type/priority, and recent cases.
- `GetStatistics` repository method computes aggregates via SQL `COUNT(*) FILTER` queries.
- `GetCaseTimeline` returns audit events for a case.
- `ListCases` with filtering and pagination.
- `CaseNumber` generated as `CAS-YYYYMMDD-NNNNNNNN-XXXXXX`.

### 3.3 Forms and Submissions

- **Form Definition** — versioned, tenant-scoped, with 13 field types.
- **Form Version** — draft/published/archived lifecycle.
- **Workflow Form Assignment** — forms assigned to specific workflow states (required/optional).
- **Form Submission** — completed forms linked to case, form, form version. `submitted_at` is immutable after creation.
- Submissions become structured facts for the rules engine via `AssembleFactsFromCase`.

### 3.4 Rules and Evaluations

- **Rule Set** — versioned, tenant-scoped collection of rules. Lifecycle: `DRAFT` → `PUBLISHED` → `ARCHIVED`.
- **Rule** — conditions (AND/OR/NOT) with typed operators, outcome, priority (first match wins).
- **Evaluation** — runs a published rule set against a frozen facts snapshot. Produces outcome + full trace tree.
- **Workflow State Rule Assignment** — rule sets assigned to workflow states, triggered on state transitions.
- **Trigger matching** — rule sets can declare triggers (`form_submitted`, `workflow_transition`, etc.).

### 3.5 Evidence

- **Evidence** — document with provenance metadata, linked to case. Types: identity, proof of residence, referral, supporting, photograph, staff note, other.
- **Verification State Machine** — `UNVERIFIED` → `VERIFIED` / `REJECTED` / `NEEDS_REVIEW`. Append-only history.
- **Evidence Document** — file metadata with server-generated `storage_key` (never exposed to clients), SHA-256 checksum, content-type allow-list.
- **Storage** — local filesystem provider with path-traversal prevention, 10MB limit.

### 3.6 Human Reviews and Decisions

- **Review Queue** — state machine: `PENDING` → `ASSIGNED` → `IN_REVIEW` → `COMPLETED` / `ESCALATED` / `WAITING_INFORMATION`. Uses PostgreSQL `SKIP LOCKED` for concurrent assignment.
- **Decision** — immutable record with `decision_maker`, `reason`, `decided_at`, `workflow_state`, `rule_evaluation_ids`, `evidence_ids`, `form_submission_id`, `review_queue_entry_id`. Versioned with supersession.
- **Decision-to-workflow mapping** — `workflow_transitions.decision_type` maps decisions to transitions.

### 3.7 Audit Trail

- **Schema isolation** — `audit.audit_events` in dedicated PostgreSQL schema, isolated from `public`.
- **Hash chain** — SHA-256 chain per organization. Each event links to previous event's hash.
- **Transactional consistency** — audit writes occur in the same database transaction as the state change. If audit write fails, state change is rolled back.
- **Integrity verification** — system verifies chains on startup and background ticks.
- **Vocabulary** — extensive `valid_audit_action` CHECK constraint with 100+ action types.

### 3.8 Organizations/Tenancy

- **Organization** — top-level tenant. All data scoped by `organization_id`.
- **Isolation layers**:
  - Middleware: `RequireSameTenant` validates JWT `organization_id` matches URL `{orgId}`.
  - Service layer: all service methods are organization-scoped.
  - Repository layer: all queries include `organization_id` filter.
  - Database: foreign keys enforce organizational ownership with `ON DELETE CASCADE`.

### 3.9 Timestamps

- **Consistent UTC usage** — all domain constructors use `time.Now().UTC()`.
- **Database defaults** — `TIMESTAMPTZ NOT NULL DEFAULT now()` for `created_at` columns.
- **Immutable timestamps** — `submitted_at` on form submissions is immutable after creation.
- **Potential inconsistency** — `cases.updated_at` is updated by application code on status changes, but workflow transitions record their own `occurred_at` in `workflow_transition_history`. These can diverge slightly (application-level vs database-level timestamp).

### 3.10 Workflow History

- **Immutable** — `workflow_transition_history` records every transition with `from_state`, `to_state`, `transition_key`, `actor_id`, `occurred_at`, `reason`, `metadata`.
- **Decision linkage** — `decision_id` column links workflow transitions to decisions.
- **Queryable** — `GET /cases/{caseId}/workflow/history` returns history for a case.

### 3.11 AI Observations from 0.8

The 0.8 milestone added comprehensive AI capabilities:

- **AI Observations** — evidence-level and case-level observations with types: `SUMMARY`, `ENTITY_EXTRACTION`, `CLASSIFICATION`, `INCONSISTENCY`, `MISSING_INFORMATION`, `RELEVANT_EVIDENCE`, `INCOMPLETE_DOCUMENTATION`.
- **Verified Facts** — when observations are accepted/corrected, they create `ai_verified_facts` with provenance.
- **Case Summaries** — AI-generated summaries with types: `FULL_SUMMARY`, `SITUATION`, `RELEVANT_INFORMATION`, `IMPORTANT_EVIDENCE`, `MISSING_INFORMATION`, `POTENTIAL_INCONSISTENCIES`, `RULE_EVALUATION_RESULTS`, `WORKFLOW_HISTORY`, `PREVIOUS_ACTIONS`, `AI_OBSERVATIONS`.
- **Document Intelligence** — AI-generated document analyses with types: `CLASSIFICATION`, `TEXT_EXTRACTION`, `STRUCTURED_EXTRACTION`, `SUMMARIZATION`, `RELEVANCE_DETECTION`.
- **Case Context** — aggregates facts from all domains for AI input. Includes authorization map.
- **Provider Abstraction** — OpenAI, Local/Ollama, Noop (default). Env-driven, off by default.
- **PII Sanitization** — document content passes through redactor before reaching provider.
- **Human Review Gates** — all AI outputs require explicit human accept/reject/correct/dismiss.

### 3.12 Authorization Boundaries

- **Authentication** — Bearer JWT tokens on every request.
- **Authorization** — role-based (`admin`, `staff`) checked at middleware and service layers.
- **AI module isolation** — no import path from `internal/ai/` to `internal/decisions/`, `internal/workflow/`, or `internal/rules/application/`.
- **Data access** — `CaseContextService` checks `CanAccessCase` before building context.

### 4.3 Ambiguous/Inconsistent Timestamps

| Issue | Severity | Details |
|---|---|---|
| `cases.updated_at` vs `workflow_transition_history.occurred_at` | Low | `cases.updated_at` is set by application code on status changes; `occurred_at` is set in the transition execution. They can diverge by milliseconds. The authoritative transition time is `occurred_at`. |
| `evidence.verified_at` vs `evidence_verification_history.verified_at` | Low | Both are set in the same transaction, but `evidence.verified_at` is a denormalized copy. The history table is the authoritative source. |
| `ai_observations.reviewed_at` vs `ai_verified_facts.verified_at` | Low | Both are set on human review, but in different tables. Should be consistent within the same transaction. |
| `form_submissions.submitted_at` is immutable | Info | This is intentional — once submitted, the timestamp cannot change. |

### 4.6 Privacy Risks

| Risk | Severity | Current Mitigation |
|---|---|---|
| AI observation content may contain PII from documents | Medium | PII redactor applied before sending to provider; `MaxObservationContentSize` limits size |
| Person records exposed via case context | Medium | `CaseContextService` checks `CanAccessCase`; context is built per-actor |
| Evidence `storage_reference` exposed in API | Low | Document `storage_key` is hidden via `json:"-"`; evidence-level `storage_reference` is the URI string |
| AI verified facts contain extracted data | Medium | Scoped to specific evidence; human review required before creation |
| Case summaries contain case data | Low | Human review required; scoped to organization |

### 4.7 Historical Reproducibility Requirements

| Aspect | Current State | Assessment |
|---|---|---|
| Rule evaluation reproducibility | ✓ | Rule set version + facts snapshot + trace tree stored |
| Decision reproducibility | ✓ | Decisions reference exact rule evaluation IDs, evidence IDs, form submission ID |
| Workflow state reproducibility | ✓ | Workflow definition version retained; transition history immutable |
| AI observation reproducibility | Partial | Input/output hashes stored; prompt not versioned; temperature = 0.3 (non-deterministic) |
| Document analysis reproducibility | Partial | Input/output hashes stored; prompt not versioned |
| Case summary reproducibility | Partial | Input/output hashes stored; prompt not versioned |

**Note:** LLM-based generation is inherently non-deterministic. Temperature is set to 0.3. This must be accepted as a design constraint for AI-assisted features.

### 4.8 Data That Must Never Be Exposed

| Data | Current Protection | Gap |
|---|---|---|
| Document `storage_key` | `json:"-"` tag — never serialized | None |
| User passwords | Not stored (external auth or hashed) | None |
| AI API keys | Env vars only, not in DB | None |
| Audit hash chain | Read-only from other modules | None |
| Evidence document bytes | Streaming endpoint with auth | None |

### 4.9 Architecture That Should NOT Be Introduced

| Architecture | Reason |
|---|---|
| Direct AI → Decision code path | Violates human-in-the-loop principle |
| AI → Workflow transition code path | Violates human-in-the-loop principle |
| AI → Rule fact injection code path | Currently safe; if introduced, must require human acceptance first |
| Event bus | Current synchronous architecture is sufficient; premature complexity |
| Shared database access across modules | Violates module boundaries; use service interfaces |
| Client-side workflow validation | Server is sole authority for workflow state |
| Editable audit events | Audit trail must remain immutable |

## 6. Proposed 0.9 Architecture

### 6.1 Operations & Impact Intelligence Layer

Add a new **operations** module for aggregated reporting and impact measurement:

```
internal/operations/
├── domain/          # Metrics, reports, aggregations
├── application/     # Report builders, aggregation services
├── api/             # Reporting endpoints
└── infrastructure/  # Materialized views, read replicas
```

### 6.2 Metric Definitions

| Metric | Formula | Source Tables |
|---|---|---|
| Case throughput | `COUNT(cases)` per day/week/month | `cases` |
| Average case duration | `AVG(closed_at - created_at)` | `cases` |
| Decision rate | `COUNT(decisions)` per reviewer per day | `decisions` |
| Approval rate | `COUNT(decisions WHERE decision = 'APPROVED') / COUNT(decisions)` | `decisions` |
| Evidence verification rate | `COUNT(evidence WHERE verification_status = 'VERIFIED') / COUNT(evidence)` | `evidence` |
| Review queue velocity | `AVG(completed_at - created_at)` from `review_queue` | `review_queue` |
| Assistance delivery rate | `COUNT(assistance WHERE status = 'COMPLETED')` per period | `assistance` |
| Follow-up completion rate | `COUNT(follow_ups WHERE status = 'COMPLETED') / COUNT(follow_ups)` | `follow_ups` |
| Rule evaluation coverage | `COUNT(evaluations) / COUNT(cases)` | `rules.evaluations`, `cases` |
| AI observation utility | `COUNT(ai_verified_facts) / COUNT(ai_observations WHERE status = 'ACCEPTED')` | `ai_verified_facts`, `ai_observations` |
| Workflow transition count | `COUNT(workflow_transition_history)` per state per day | `workflow_transition_history` |
| Case outcome distribution | `COUNT(decisions) GROUP BY decision` | `decisions` |

### 6.3 Data Model Additions

1. **Materialized views** for common aggregations:
   - `mv_case_metrics_daily` — daily case counts, durations, status breakdown
   - `mv_decision_metrics_daily` — daily decision counts, approval rates
   - `mv_review_metrics_daily` — daily review queue metrics

2. **Outcome follow-up table** (optional):
   - `case_outcomes` — long-term outcome tracking linked to decisions
   - `outcome_date`, `outcome_type`, `notes`, `recorded_by`

3. **Retention policies**:
   - `ai_observations` — configurable retention (default: 2 years)
   - `case_summaries` — configurable retention (default: 2 years)
   - `document_analyses` — configurable retention (default: 2 years)
   - `workflow_transition_history` — indefinite (audit requirement)

### 6.4 API Additions

```
GET /organizations/{orgId}/operations/metrics/cases
GET /organizations/{orgId}/operations/metrics/decisions
GET /organizations/{orgId}/operations/metrics/reviews
GET /organizations/{orgId}/operations/metrics/assistance
```

### 6.5 Authorization

- All operations endpoints require `AuthRequired` + `RequireSameTenant` + `RequireAnyRole("admin", "staff")`.
- Metrics are tenant-scoped; no cross-tenant aggregation.
- No PII in metric responses.

### 6.6 Privacy & Security

- **No PII in metrics** — all aggregations are counts/sums/rates.
- **Tenant isolation** — all queries filtered by `organization_id`.
- **Read-only** — operations endpoints are GET-only; no mutations.
- **Cache control** — materialized views refreshed on schedule, not real-time.

## 8. Blockers

**No critical architectural blockers found.**

The repository is architecturally ready for Operations & Impact Intelligence. The existing foundation (workflow engine, case management, rules, evidence, audit, AI observations) provides all necessary authoritative data sources. The main work is building the aggregation and reporting layer on top of existing data.

### Conditions

1. **Do not introduce AI → Decision/Workflow/Rules code paths.** The current isolation must be preserved.
2. **Do not expose PII in metrics.** All reporting endpoints must return aggregated data only.
3. **Preserve audit integrity.** Any new tables or views must not break the existing hash chain.
4. **Maintain tenant isolation.** All new queries must be organization-scoped.
