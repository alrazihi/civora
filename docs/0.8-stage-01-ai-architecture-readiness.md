## 1. Executive Summary

## 3. Evidence Domain Analysis (0.7 Foundation Layer)

The evidence domain (completed in 0.7) is the critical integration point for AI. AI will observe evidence and produce structured observations; humans verify them.

### 3.1 Evidence Entity (`internal/evidence/domain/evidence.go`)

**Evidence** entity fields:
- `ID` — UUID
- `CaseID` — FK to case
- `OrganizationID` — Tenant isolation
- `PersonID` — FK to person (optional)
- `EvidenceType` — ENUM (document, image, audio, video, text)
- `Status` — Verification status (see 3.3)
- `Metadata` — JSONB for flexible extraction data
- `CreatedAt`, `UpdatedAt` — Timestamps
- `CreatedBy`, `UpdatedBy` — User FKs

**Key design decisions:**
- `Metadata` as JSONB allows storing AI-extracted data (summaries, entities, classifications) without schema changes
- `OrganizationID` at entity level enforces tenant isolation at the domain layer

### 3.2 Document Management (`internal/evidence/domain/document.go`)

**Document** entity:
- `ID` — UUID
- `EvidenceID` — FK
- `OrganizationID` — Tenant isolation
- `StorageProvider` — ENUM (LOCAL, S3, GS, AZURE) — abstract interface allows future cloud migration
- `StorageKey` — Server-generated for security
- `Filename` — Original filename (sanitized)
- `ContentType` — MIME type (allow-listed)
- `FileSize` — Integer (10MB hard limit)
- `Checksum` — SHA-256 hash
- `UploadedAt` — Timestamp
- `UploadedBy` — User FK

**Infrastructure** (`internal/evidence/infrastructure/storage/`):
- `StorageProvider` interface — abstract storage operations
- `LocalStorageProvider` — concrete implementation with server-generated keys
- `SanitizeFileName()` — removes path components, dangerous characters
- `ValidateContentType()` — checks against allow-list (`application/pdf`, `image/jpeg`, etc.)
- SHA-256 checksum computed on storage
- 10MB size limit enforced

**Security highlights:**
- Server-generated storage keys prevent key guessing
- Filename sanitization prevents path traversal
- Content-type allow-list prevents malicious uploads
- Checksum integrity verification

### 3.3 Verification Lifecycle

**VerificationStatus** enum: `UNVERIFIED` → `VERIFIED` / `REJECTED` / `NEEDS_REVIEW`

**VerificationRecord** entity:
- `ID` — UUID
- `EvidenceID` — FK
- `Status` — The verification status
- `VerifiedBy` — User FK
- `Notes` — Optional text
- `CreatedAt` — Timestamp

**Immutability:** Once a verification record is created, it cannot be modified — only new records can be appended. This creates an immutable history chain.

**Service operations** (`internal/evidence/application/service.go`):
- `AddEvidence()` — Creates evidence with UNVERIFIED status
- `VerifyEvidence()` — Transitions to VERIFIED (creates verification record)
- `RejectEvidence()` — Transitions to REJECTED (creates verification record)
- `MarkEvidenceForReview()` — Transitions to NEEDS_REVIEW (creates verification record)
- `UploadDocument()` — Attaches document to evidence
- `GetDocumentStream()` — Streams document content
- `ListDocuments()` — Lists documents for an evidence item
- `DeleteDocument()` — Deletes document (marks as deleted)

## 4. Decisions Domain Analysis

The decisions domain (`internal/decisions/`) captures all human decisions. AI must never produce decisions directly.

### 4.1 Decision Entity (`internal/decisions/domain/decision.go`)

**DecisionType** enum: `APPROVED`, `REJECTED`, `NEEDS_MORE_INFORMATION`, `ESCALATE`

**Decision** entity:
- `ID` — UUID
- `CaseID` — FK
- `OrganizationID` — Tenant isolation
- `DecisionType` — Above enum
- `Reasoning` — Text field for justification
- `DecidedBy` — User FK
- `SupersededByID` — For decision replacement (audit trail)
- `CreatedAt` — Timestamp

### 4.2 Decision Service (`internal/decisions/application/service.go`)

- `MakeDecision()` — Creates a new decision
- `SupersedeDecision()` — Marks a previous decision as superseded
- `GetDecision()` / `GetDecisionHistory()` / `ListDecisions()` — Read operations
- All operations are org-scoped via `OrganizationID`

### 4.3 Decision API Handler (`internal/decisions/internal/decisions/api/handler.go`)

- Route: `/api/v1/decisions` (POST, GET, GET/{id}/history)
- Middleware: Auth middleware + `RequireSameTenant`
- Role requirement: `admin` or `staff`

**Critical separation confirmed:** Decision-making requires authenticated human users with admin/staff roles. AI has no pathway to create or supersede decisions.

## 5. Rules Engine Analysis

The rules engine (`internal/rules/`) evaluates case rules. AI must not influence rules evaluation — it can only provide observations for human consideration.

### 5.1 Pure Evaluation (`internal/rules/domain/engine.go`)

- `EvalRules()` — Pure function, no I/O
- `ResolveFact()` — Takes a `FactResolver` interface, resolves facts from external context
- No network calls, no file I/O, no database access
- Deterministic, testable, reproducible

### 5.2 RuleSet and Conditions

**RuleSet** (`internal/rules/domain/rule_set.go`):
- `Name`, `Description`
- `Status` — DRAFT, PUBLISHED, ARCHIVED
- `Version` — Integer for versioning
- `Conditions` — JSONB (flexible condition definitions)
- `Outcomes` — JSONB (structured outcomes)

**Condition operators** (`internal/rules/domain/rule.go`):
`eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `in`, `not_in`, `is`, `is_not`, `exists`, `not_exists`, `contains`, `contains_all`, `regex`

### 5.3 Case Integration (`internal/rules/application/case_integration.go`)

**CaseRuleIntegrationService** provides:
- `AssembleCaseFacts()` — Collects facts from form submissions, evidence metadata, etc.
- Uses `FormSubmissionFinder` interface from `shared` package
- Fact keys follow naming convention: `case.field_name`, `evidence.metadata_key`

**This is the AI insertion point:** AI observations stored in evidence `Metadata` will become available as facts to the rule engine via `AssembleCaseFacts()`, following the existing pattern.

### 5.4 Rules API (`internal/rules/internal/rules/api/handler.go`)

- Routes: `/api/v1/rule-sets` (CRUD), `/api/v1/rule-sets/{id}/evaluations` (GET)
- Middleware: Auth + `RequireSameTenant`
- Service interfaces use DTOs for input/output

## 6. Audit Domain Analysis

The audit domain (`internal/audit/`) provides hash-chained, immutable audit records — essential for AI traceability.

### 6.1 Audit Event (`internal/audit/domain/event.go`)

**AuditEvent** fields:
- `ID` — UUID
- `OrganizationID` — Tenant isolation
- `EventType` — String (e.g., "evidence.added", "decision.made")
- `ActorUserID` — User FK
- `TargetType`, `TargetID` — What was acted upon
- `Metadata` — JSONB for event-specific data
- `PreviousHash` — Hash of previous event in chain
- `Hash` — Hash of this event (computed from fields)
- `CreatedAt` — Timestamp

### 6.2 Audit Service (`internal/audit/application/service.go`)

- `RecordEvent()` — Records outside transaction
- `RecordEventInTx()` — Records within transaction (for atomicity)
- Hash chain validation on every write
- Events are immutable after recording

### 6.3 Shared Audit Helper (`internal/shared/audit.go`)

`RecordAuditEventInTx()` — Helper function that any service can call to record audit events within an existing transaction, ensuring atomicity.

**AI audit strategy:** Every AI observation will be recorded as an audit event:
- Event type: `ai.observation.created`
- Metadata: Includes model name, model version, input data hashes, output hash, confidence scores
- ActorUserID: NULL (system-generated) or a service account

## 7. Authentication & Authorization

### 7.1 JWT Auth (`internal/middleware/auth.go`)

**JWTService** provides:
- `GenerateToken()` — Creates JWT with userID, orgID, role
- `VerifyToken()` — Verifies JWT signature and expiration
- Context functions: `UserIDFromContext()`, `OrganizationIDFromContext()`, `RoleFromContext()`
- `RequireSameTenant()` — Middleware ensuring the authenticated user's orgID matches the resource's orgID

### 7.2 Role-Based Access Control

Roles (from config or database):
- **admin** — Full access
- **staff** — Case management access
- **user** — Basic access (self-service)

### 7.3 Middleware Chain (`internal/server/server.go`)

Order: CORS → SecureHeaders → JWTAuth → Idempotency → Handler

**Security implications for AI:**
- AI observation creation will require authenticated admin/staff access (same as evidence verification)
- All AI operations will be org-scoped via JWT orgID
- Idempotency middleware prevents replay attacks on AI observation submissions

## 11. Threat Model Alignment

The repository includes `docs/threat-model.md` and `docs/principles.md` which establish security constraints. AI integration must align with these.

### 11.1 Key Principles from `docs/principles.md`

1. **Human oversight required** — All decisions must be human-made; AI can only assist
2. **Immutability** — Audit records and verification history are append-only
3. **Tenant isolation** — All data is scoped by organization_id at every layer
4. **Least privilege** — Services have minimal permissions; users have RBAC
5. **No data exfiltration** — Local storage option exists; S3/GS/Azure providers optional

### 11.2 Threat Model from `docs/threat-model.md`

Documented threats include: data leakage, unauthorized access, tampering, repudiation, and denial of service. Controls: encryption at rest (storage), TLS everywhere (server), RBAC (middleware), hash chaining (audit), input validation (evidence storage).

**AI-specific threats to address in Stage 1 design:**
- Model prompt injection (mitigated: AI only reads evidence, doesn't write decisions)
- AI hallucination (mitigated: AI output is advisory, human verification required)
- AI data poisoning (mitigated: evidence documents are validated, checksums verified)
- AI privacy leakage (mitigated: local-first storage, no external calls without consent)

## 12. Architecture Questions for Stage 2

The following questions must be answered in the Stage 2 design phase (AI Observation Engine):

### 12.1 AI Placement & Boundaries

**Question:** Where in the codebase will AI services live?

**Recommended answer:** `internal/ai/` module following the same domain/application/api/infrastructure pattern. AI services should be consumers of existing ports (repositories, services) and providers of new ports (fact resolvers, observation stores).

**Constraint:** AI must only write to evidence `metadata` (new field or sub-object) and create new audit events. It must never:
- Create or modify decisions
- Transition case/workflow status
- Bypass rules evaluation
- Skip human verification steps

### 12.2 Access Control for AI Operations

**Question:** What authentication does the AI service use?

**Recommended answer:** AI operations should run under a service account with `admin` role, authenticated via JWT. The `ActorUserID` in audit events should reference this service account. AI observation creation API endpoints should require admin role (same as evidence verification).

### 12.3 Observation Provenance

**Question:** How will we track which model produced each observation?

**Recommended answer:** Every AI observation must include in audit metadata:
- Model name and version (e.g., "gpt-4o-mini-v1")
- Model provider (e.g., "openai")
- Input data hashes (hash of the documents/fields the model processed)
- Output hash (hash of the raw model response)
- Confidence scores or structured output
- Processing timestamp and duration
- Whether the model used a local or remote provider

### 12.4 Failure Handling & Degradation

**Question:** What happens if the AI provider is unavailable?

**Recommended answer:**
- Graceful degradation: AI observations become `UNVERIFIED` and require manual review
- Retry queue with exponential backoff for transient failures
- Circuit breaker pattern for provider health
- Local fallback: if no AI provider is configured, system operates in "human-only" mode (current 0.7 behavior)
- All failures logged as audit events with `ai.observation.failed` type

### 12.5 Provider Abstraction

**Question:** How will we support multiple AI providers?

**Recommended answer:** Define an `AIProvider` interface in `internal/ai/domain/` with methods:
- `ExtractObservations(ctx, documents) ([]Observation, error)`
- `SummarizeText(ctx, text) (Summary, error)`
- `ClassifyContent(ctx, content) (Classification, error)`

Implementations: `internal/ai/infrastructure/openai/`, `internal/ai/infrastructure/anthropic/`, `internal/ai/infrastructure/local/`. Configuration in `config.go` selects the active provider via environment variables.

### 12.6 Tenant Isolation

**Question:** How does AI ensure tenant data doesn't leak?

**Recommended answer:**
- AI service receives `OrganizationID` from the request context
- All model calls include `OrganizationID` for logging/tracing
- Multi-model router routes to organization-specific model endpoints if configured
- No cross-tenant data in model prompts
- Local models preferred for PII-sensitive cases (configurable per organization)

### 12.7 Security & Data Protection

**Question:** How is PII handled in AI processing?

**Recommended answer:**
- PII is not sent to external models by default
- For external providers, PII must be masked or removed before sending
- Local models are the default; external providers are opt-in per organization
- Document storage keys are server-generated; AI receives only storage keys, not raw file paths
- All AI processing happens server-side; no client-side model calls

### 12.8 Audit & Reproducibility

**Question:** How can we audit and reproduce AI observations?

**Recommended answer:**
- Every observation creates an audit event with input/output hashes
- AI service logs full prompts and responses to a secure audit log (encrypted at rest)
- Model version pinning: `config.go` specifies exact model version
- If `OrganizationID` + `EvidenceID` + `ModelVersion` + `InputHash` are provided, the observation can be reproduced
- Audit events are immutable and hash-chained

## 14. Verdict

**GO**

The repository at `218184d` provides all architectural foundations required for AI integration:

1. **Secure document ingestion** — Evidence domain with validated uploads, checksum verification, tenant isolation
2. **Human-in-the-loop verification** — Immutable verification workflow ensures AI output is always vetted
3. **Separation of concerns** — AI cannot make decisions; decisions domain requires authenticated humans with admin/staff roles
4. **Audit trail** — Hash-chained audit events will capture full AI provenance
5. **Rules integration** — Existing fact resolution interfaces support AI-provided facts without architectural changes
6. **Clean architecture** — Domain/application/api/infrastructure layering and shared interfaces enable non-invasive AI module addition
7. **Threat model alignment** — Documented security principles cover AI-specific concerns
8. **Test coverage** — Unit tests pass (30 Go tests, 22 provider tests); e2e tests pass (74 total, 5 AI-specific).

**Recommended next step:** Proceed to Stage 2 — Design and implement `internal/ai/` module with provider abstraction, observation storage, and audit integration.
