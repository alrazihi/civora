## 4. AI Module Inspection

Commit `8e2e063` adds a complete AI observation module. Here is what exists:

### 4.1 Domain (`internal/ai/domain/observation.go`, 176 lines)

**Entities and types:**
- `ObservationType`: SUMMARY, ENTITY_EXTRACTION, CLASSIFICATION, INCONSISTENCY (hardcoded enum)
- `ObservationStatus`: PENDING_REVIEW, ACCEPTED, REJECTED (human review lifecycle)
- `ObservationSource`: AI_MODEL, HUMAN
- `ModelInfo`: Name, Version, Provider
- `Observation` struct: ID, OrganizationID, EvidenceID, Type, Source, Status,
  Model, Content (JSONB-like `map[string]any`), Confidence, InputHash, OutputHash,
  CreatedAt, CreatedBy, ReviewedAt, ReviewedBy, ReviewNotes
- `DocumentContent` struct: DocumentID, FileName, ContentType, Content ([]byte), Checksum
- `ProviderOptions` struct: Types, MaxTokens
- `ObservationRepository` interface with 6 methods: Save, SaveTx, FindByID,
  FindByEvidence, UpdateStatus, CountByEvidence
- `NewObservation()` — validates org ID and evidence ID are non-nil; defaults Source
  to AI_MODEL and Status to PENDING_REVIEW
- `Observation.Accept(reviewerID, notes)` / `Observation.Reject(reviewerID, notes)` —
  mutate status + set reviewed_at/reviewer/notes
- Constants: `MaxObservationContentSize = 100_000` (defined but **not enforced** in
  `NewObservation`)

**Domain validation gaps:**
- No validation of `Content` size (the `MaxObservationContentSize` constant is never
  checked).
- No validation of `Confidence` range (could be > 1.0 or negative).
- No validation of `Type` against the allowed set (the DB has a CHECK constraint,
  but the domain `NewObservation` does not enforce it).
- `ObservationParams` struct has fields but several are silently dropped — the
  constructor never validates that `Content` is non-nil or well-formed.

### 4.2 Application Service (`internal/ai/application/service.go`, 373 lines)

**AIService struct:**
```go
type AIService struct {
    repo         domain.ObservationRepository
    evidenceRepo EvidenceRepository  // local interface with FindByID, ListDocuments, SaveTx
    userChecker  shared.UserChecker
    auditor      auditdomain.EventRecorder
    provider     AIProvider
}
```

**Methods:**
1. `GenerateObservations(ctx, params)` — the core AI entry point.
   - Validates actor belongs to org (`userChecker.BelongsToOrganization`).
   - Finds evidence by ID.
   - Lists documents for the evidence (up to 50).
   - Builds `DocumentContent` slice from document metadata (notably: **does NOT
     retrieve actual document file contents** — only metadata).
   - Calls `provider.GenerateObservations(ctx, req)`.
   - On provider error: records `ai.observation.failed` audit event, returns
     `ErrAIProviderUnavailable`. **No observation is persisted on failure.**
   - On success: records `ai.observations_generated` audit event, then for each
     result creates an `Observation` via `NewObservation`, records
     `ai.observation.created` audit event, and calls `repo.Save`.
   - Returns `GenerateObservationsResult` with DTO-serialized observations.

2. `ListObservations(ctx, params)` — validates evidence exists, delegates to repo.

3. `ReviewObservation(ctx, params)` — validates reviewer belongs to org, finds
   observation, calls `Accept` or `Reject` on domain entity, calls
   `repo.UpdateStatus`, records audit event.

**Critical observations about the flow:**
- **Observations are created with `CreatedBy: nil`** (line 206 of service.go).
  The audit event records `ActorID: &params.ActorID` (the human who triggered
  generation), but the observation entity itself has no `created_by`. This means
  provenance of *who* triggered generation is in the audit log but not on the
  observation record.
- **Observations start in PENDING_REVIEW and require human Accept/Reject.** This
  is correct — AI output is never auto-accepted.
- **No link from approved observations to facts or rules.** Accepted observations
  sit in the `ai_observations` table but are never fed into `AssembleFactsFromCase`
  or any rule evaluation path.
- **No link from observations to decisions or review queue.** The review queue and
  decision services (`internal/review_queue/`, `internal/decisions/`) do not
  reference `ai_observations` at all.
- **No organization-level opt-in/out toggle.** The only control is a global
  `CIVORA_AI_ENABLED` env flag (default false). There is no per-organization
  setting in the database to enable/disable AI for a specific tenant.
- **No retry, backoff, or circuit breaker.** If the provider fails, the error is
  returned immediately. No queued retry, no circuit breaker.
- **No rate limiting on AI endpoints.** The AI handler routes apply the same
  global rate limiter as other endpoints, but there is no AI-specific rate
  limiting.
- **No cancellation propagation.** The provider call uses `ctx`, but there is no
  explicit timeout wrapping on the provider call in `GenerateObservations`.
  The OpenAI provider sets its own HTTP client timeout (60s), but the local
  provider sets 120s.

### 4.4 Infrastructure — Postgres Repository (`internal/ai/infrastructure/postgres/observation_repository.go`, 181 lines)

- `PostgresObservationRepository` with `Save`, `SaveTx`, `FindByID`,
  `FindByEvidence`, `CountByEvidence`, `UpdateStatus`.
- All queries scope by `organization_id` (tenant isolation at DB layer).
- `UpdateStatus` writes `reviewed_at` with `sql.NullTime{Time: readTime(), Valid: true}`
  (line 139) — `readTime()` returns `time.Now().UTC()`. No transaction wrapper
  for the update (no `UpdateStatusTx` variant, despite the domain repo interface
  having `SaveTx`). Audit event recording and status update are **not atomic**
  — if the repo update succeeds but the audit record fails (or vice versa),
  the state diverges. Compare with the evidence verification path which uses
  `UpdateVerificationTx` + `SaveVerificationHistoryTx` inside a single transaction.

### 4.5 Infrastructure — Providers

**OpenAI Provider** (`provider/openai.go`, 335 lines):
- Implements OpenAI Chat Completions API (compatible with any OpenAI-compatible
  endpoint including Ollama via `LocalProvider`).
- `systemPrompt()` (line 277): hardcodes a system prompt: *"You are CIVORA's AI
  evidence analysis assistant. You extract structured observations from case
  evidence documents. All observations require human verification before use in
  decision-making. Do not make judgments or recommendations; only extract facts,
  summaries, entities, and identify potential inconsistencies."*
- **No prompt template system** — the system prompt and user prompt are hardcoded
  strings with no versioning, externalization, or audit of prompt variants.
- **No PII sanitization** — document content is included in the prompt verbatim
  (truncated to 5000 chars per document, max 10 documents). If documents contain
  PII, it is sent to the external model as-is.
- **Output hash** is computed as SHA-256 of the raw response body (`computeSHA256`).
- **Input hash** is computed from document IDs, filenames, content types, checksums,
  requested types, and max tokens (`computeInputHash`).
- Temperature is hardcoded to 0.3 (line 148).
- `response_format: json_object` is requested (line 146) to enforce JSON output.
- Response parsing (`parseObservations`, line 281) silently drops observations
  with unrecognized types (line 291-293). No validation of the JSON structure
  beyond the top-level `observations` array.
- **HTTP status check:** any non-200 status returns an error (line 176-177).
  The error message includes the response body, which could leak API error
  details.
- Default model: `gpt-4o-mini`. Default base URL: `https://api.openai.com/v1`.

**Local Provider** (`provider/local.go`, 76 lines):
- Wraps `OpenAIProvider` with `SkipAuth: true` and configurable base URL/model.
- Default base URL: `http://localhost:11434/v1` (Ollama default).
- Default model: `llama3`.

**Noop Provider** (`provider/noop.go`, 31 lines):
- Returns `ErrProviderDisabled` ("AI provider is not configured or is disabled")
  on every call. This is the **default** when `AI.Enabled` is false or no provider
  is configured (per `config.go:113` — `CIVORA_AI_ENABLED` defaults to false).

## 6. Current Architecture — AI Integration Boundary Analysis

### 6.1 The CIVORA Pipeline (intended)

```
Documents → Evidence → AI Observation → Human Verification → Structured Case Fact
     → Rules → Evaluation → Human Review → Human Decision → Workflow → Audit
```

### 6.2 Where Does AI Belong (correctly)

Per `docs/principles.md` (Principle 7: Human-centered) and `docs/hostile-review.md`:

- AI **may** summarize, extract, classify, identify inconsistencies, identify
  missing information, help organize case information, answer questions grounded
  in authorized case data.
- AI **must NOT** make final eligibility decisions, approve/reject cases, silently
  modify case data/evidence, bypass rules, bypass human review, transition
  workflow state, invent evidence, or present unsupported claims as facts.

### 6.3 Where AI Does NOT Belong

**Decision-making:** The `decisions` domain (`internal/decisions/`) is reachable
only through authenticated human actors. `DecisionService.MakeDecision` and
`ReviewQueueService.CompleteReview` both require `ActorID` from a valid JWT.
The AI module has **no dependency on** and **no reference from** the decisions or
review_queue services. Good — AI cannot directly create decisions.

**Workflow state:** The `workflow` module's `WorkflowService.ExecuteTransition`
is only called from `DecisionService.MakeDecision` (Path A) and
`ReviewQueueService.CompleteReview/EscalateReview` (Path B), both of which
require a human actor. The AI `GenerateObservations` flow does **not** call any
workflow transition. Good — AI cannot transition workflow state.

**Rules evaluation:** The rules engine (`internal/rules/domain/engine.go:103`) is
pure and called from `CaseRuleIntegrationService.EvaluateCaseRules` during workflow
transitions (triggered by `CaseService.OnTransition`). The AI module does **not**
inject facts into `AssembleFactsFromCase`. So AI currently does not influence rules —
but this also means AI observations are **not usable by rules at all**, which is
an integration gap rather than a safety property.

### 6.4 The Critical Gap: AI Observations Are Siloed

This is the **single most important finding** of this audit:

1. **Observations are stored** in `ai_observations` table, scoped by `evidence_id`.
2. **Observations can be human-accepted or human-rejected** via the review UI.
3. **But accepted observations are never read by any other system.** There is no
   code path that:
   - Reads accepted observations to assemble `facts["evidence"]` for the rules engine.
   - Reads accepted observations to populate the `Evidence.metadata` JSONB field
     (which the rules engine *could* read if facts were assembled from it).
   - Links observations to `ReviewQueueEntry.EvidenceIDs` or `Decision.EvidenceIDs`.
   - Surfaces observations in the reviewer workspace UI alongside rule evaluations.
   - Links `WorkflowTransitionHistory` to observations.

In other words: **AI produces observations, humans review/accept them, and then
the accepted observations are discarded from the pipeline.** The observations have
no effect on rules evaluation, decisions, or workflow. This means the AI work
delivers **observability** but not **utility** — it does not yet fulfill the
"identify missing information" or "help organize case information" role in a way
that influences the case pipeline.

This is a **functional incompleteness**, not a **safety violation**. The CIVORA
principle "AI must not become the decision-maker" is upheld — but only because
the AI output goes nowhere, not because of an intentional architectural
decision.

### 6.5 AI Module Wiring in main.go

`cmd/civora/main.go:251-266`:
```go
aiObsRepo := aiinfrapostgres.NewPostgresObservationRepository(db.DB)
var aiProvider aiapplication.AIProvider
switch {
case cfg.AI.Enabled && cfg.AI.Provider == "openai" && cfg.AI.OpenAIAPIKey != "":
    aiProvider = aiprovider.NewOpenAIProvider(...)
case cfg.AI.Enabled && cfg.AI.Provider == "local" && cfg.AI.LocalEnabled:
    aiProvider = aiprovider.NewLocalProvider(...)
default:
    aiProvider = aiprovider.NewNoopProvider()
}
aiService := aiapplication.NewAIService(aiObsRepo, evidenceRepo, domain.NewOrganizationUserChecker(userRepo), auditService, aiProvider)
aiHandler := aiapi.NewHandler(aiService)
...
aiHandler.RegisterRoutes(srv.Router(), authMiddleware)
```

**Issues:**
- `evidenceRepo` is the `evidencepostgres.PostgresEvidenceRepository` (the full
  repo). The AI service's local `EvidenceRepository` interface only needs
  `FindByID`, `ListDocuments`, `SaveTx` — but it receives the full concrete type.
  This is a wider interface than needed (dependency hygiene concern, not a bug).
- The provider switch has no validation that config values (base URL, model) are
  non-empty for the OpenAI/Local cases beyond `APIKey != ""` for OpenAI. If
  `OpenAIModel` is empty, `NewOpenAIProvider` defaults it.
- `NewAIService` accepts `auditor auditdomain.EventRecorder` and wraps it; all
  audit calls are guarded by `if s.auditor != nil` checks — defensive but
  consistent with the existing pattern.

### 6.6 Observation Content Model

`Observation.Content` is `map[string]any` — a free-form JSONB blob. There is **no
schema enforcement** on what an observation's `content` looks like. The OpenAI
provider parses the model response into `content` with a `text` key for
summaries or `entities` for entity extraction, but:
- The domain does not validate these shapes.
- Different observation types could have wildly different content structures.
- There is no content-addressable representation for reproducibility.

## 9. Audit

### 9.1 Audit Events Recorded

| Event | Triggered by | Metadata | Audit scope |
|---|---|---|---|
| `ai.observations_generated` | `GenerateObservations` | count, model, model_version, provider, types_requested | Per org |
| `ai.observation.created` | `GenerateObservations` (per observation) | evidence_id, observation_type, model, confidence, input_hash, output_hash | Per org |
| `ai.observationaccepted` | `ReviewObservation` | evidence_id, status, notes | Per org |
| `ai.observation.rejected` | `ReviewObservation` | evidence_id, status, notes | Per org |
| `ai.observation.failed` | `GenerateObservations` (provider error) | reason, model | Per org |

### 9.2 Audit Issues Found (BLOCKED)

1. **Audit events in `GenerateObservations` are NOT in the same transaction as the
   observation save.** Lines 163-182 record the `ai.observations_generated` audit
   event using `shared.RecordAuditEventInTx(ctx, nil, ...)` — note `nil` for the
   transaction. Then lines 211-231 record `ai.observation.created` events also
   with `nil` tx. Then line 233 calls `repo.Save(ctx, obs)` outside any
   transaction. This means:
   - The audit events and the observation persistence are **not atomic**.
   - If `repo.Save` fails after audit events are recorded, the audit log shows
   observations created that don't exist in the DB.
   - If `repo.Save` succeeds but audit recording fails, observations exist
   without audit trail.
   - The existing CIVORA pattern (`shared.RecordAuditEventInTx` with a real `*sql.Tx`
   inside `database.InTransaction`) is **not followed** here.

2. **`RecordObservation.Save` does not use `SaveTx`.** The domain repo interface
   has `SaveTx(ctx, tx, o)`, but `AIService.GenerateObservations` calls
   `s.repo.Save(ctx, obs)` (no transaction) at line 233. The observations are
   saved one-by-one outside a transaction, breaking the atomicity that the
   evidence module achieves (where `SaveTx` is used inside `InTransaction`).

3. **`ReviewObservation` audit events are NOT transactional with `UpdateStatus`.**
   `s.repo.UpdateStatus` (line 329) is called outside any transaction, then
   `s.recordAudit` (line 337) is called. If the audit record fails, the status
   is already changed. If the status update fails, no audit event is recorded
   but the intent to accept/reject is lost.

4. **`actorID` vs `nil` created_by:** `CreatedBy` on the observation is always nil
   (system/AI-generated). The `ActorID` in the audit event is the human who
   triggered generation. This is semantically correct (AI created it), but the
   field `created_by` being nullable and always nil reduces provenance clarity.

### 9.3 Hash Chain Integrity

The `ai.observations_generated` and `ai.observation.failed` events use
`shared.RecordAuditEventInTx(ctx, nil, ...)` — passing `nil` as the transaction
parameter. Since the auditor (`AuditService`) implements both `RecordEvent` (non-tx)
and `RecordEventInTx`, and the `nil` tx causes the `txEventRecorder` interface
type assertion to fail, the call falls through to `RecordEvent` (non-transactional).
The hash chain is still maintained (each `RecordEvent` call reads the previous
hash and writes the new one atomically in its own DB call), so the chain integrity
is preserved — but the audit event and the domain write it describes are not
atomic. This is the same gap as #1 above.

## 10. Evidence Verification Integration (AI + Verification)

### 10.1 What AI Reads (Inputs)

- `GenerateObservations` finds an evidence item by ID.
- It calls `evidenceRepo.ListDocuments(ctx, orgID, evidenceID, 50, 0)` to get
  document metadata.
- It builds `DocumentContent` with: DocumentID, FileName, ContentType, Checksum.
- **It does NOT retrieve the actual document file bytes** — `DocumentContent.Content`
  (`[]byte`) is left as nil. The OpenAI provider's `buildPrompt` includes
  `doc.Content` in the prompt (line 251-256), but since `Content` is nil, the
  prompt would contain empty string previews.

**This is a functional bug:** AI cannot actually read document contents. The
`DocumentContent` struct has a `Content []byte` field, but the service never
populates it. The OpenAI provider's `buildPrompt` method iterates over documents
and includes `doc.Content` as the document body, which is always empty.

This means the AI provider receives document metadata (filename, content type,
checksum) but **not the actual document content**. Observations are generated
from metadata alone, which severely limits their usefulness.

### 10.2 What AI Writes (Outputs)

- Observations stored in `ai_observations.content` (JSON `map[string]any`).
- **AI does NOT modify evidence metadata.** Observations are standalone records
  that reference evidence, not augmentations of it.
- No `evidence.metadata_updated` is triggered by AI.
- No evidence verification status is changed by AI.

### 10.3 Verification Status Interaction

AI does **not** check the evidence's verification status before observing. An
observation could be generated from evidence that is UNVERIFIED, REJECTED, or
VERIFIED — there is no gate. This is acceptable for an advisory system (AI
summarizes what it sees), but if AI observations were to feed rules, the
verification status should be a gating factor (rules should not trust AI
observations from REJECTED evidence).

## 15. Privacy & Sensitive Data

### 15.1 PII in AI Processing

The `DocumentContent` struct carries `FileName`, `ContentType`, `Checksum` —
but not the file bytes. This means PII is **not** currently leaked to AI models
because document content is not retrieved. However, this is a side effect of the
bug in §6.4 (Content is nil), not an intentional privacy design. If the content
retrieval bug is fixed, PII will flow to the model unless a sanitization layer
is added.

### 15.2 Storage

- Observations stored in PostgreSQL alongside other case data (not in a separate
  secure store).
- `ai_observations.content` is JSONB — no encryption at rest beyond what the DB
  provides (PostgreSQL TDE if configured by operator).
- Input/output hashes are stored for reproducibility, but **raw prompts and
  responses are not logged** (a privacy-positive choice, but reduces debuggability).

### 15.3 Data Retention

- `AIConfig` has no retention setting.
- Audit retention (`AuditConfig.RetentionDays`, default 2555 = 7 years) applies
  to `audit.audit_events` which includes AI events, but does not apply to
  `ai_observations` table itself.
- No mechanism to delete or export AI observations.

## 18. Proposed Architecture (for Stage 2)

The audit does not implement features, but to evaluate readiness, the proposed
Stage 2 architecture is documented here as the target the current code must
align with:

### 18.1 AI Integration Boundary

AI belongs in the **"Observation" slot** of the pipeline:
```
Documents → Evidence → [AI Observation] → Human Verification → Structured Case Fact
```

AI output must flow through **two** mandatory human gates before affecting any
consequential system:

1. **Observation review** (human Accept/Reject per observation) — already
   partially implemented.
2. **Evidence verification** (human verifies the evidence item) — already
   implemented in 0.7.

Only after both gates can an observation's content be considered for rule
evaluation as a `facts["evidence"]` or `facts["ai_observation"]` source.

### 18.2 Proposed Data Model Additions

1. **Observation-to-fact bridge:** Add a method to the rules fact assembly
   (`AssembleFactsFromCase`) to include accepted AI observations:
   ```go
   // facts["evidence"][evidenceID]["ai_observations"] = [...accepted observations]
   ```
   This requires a read interface on `ObservationRepository` that returns
   accepted observations by evidence ID.

2. **Observation-to-review-queue link:** Add `observation_ids` to
   `review_queue` provenance so reviewers can see AI observations in the
   decision workspace. This is a foreign-key-free JSON array (matching the
   existing `evidence_ids` and `rule_evaluation_ids` pattern).

3. **Per-organization AI settings table:** A `organization_ai_settings` table
   (or reuse an org settings JSONB) to toggle AI on/off per tenant, set model
   preferences, and enforce PII handling policies.

### 18.3 Proposed Audit Requirements

- All `GenerateObservations` audit events must be recorded **in the same
  transaction** as the observation save, following the existing
  `shared.RecordAuditEventInTx(ctx, tx, ...)` pattern used by the evidence
  module.
- `ReviewObservation` status update and audit must be atomic.
- Input/output hashes must be SHA-256 of the actual document content (once
  retrieved), not just metadata.

### 18.4 Proposed Provider Abstraction

Extend `AIProvider` to be organization-aware:
```go
type AIProvider interface {
    GenerateObservations(ctx context.Context, req ProviderRequest) ([]ObservationResult, error)
    ProviderInfo() domain.ModelInfo
}
```
Keep as-is for now. Add a `ProviderRouter` that selects per-organization
provider in Stage 2.1.

### 18.5 Proposed Human-Control Requirements

- Observations **must** default to PENDING_REVIEW.
- Accepted observations **must** retain their provenance (model, input hash,
  output hash, confidence).
- Observations **must not** be editable after creation.
- Reviewers **must** see the evidence verification status when reviewing
  observations.
- The `decision_type` → workflow transition mapping **must not** be influenced
  by AI observations directly.

## 19. Reproducibility

| Aspect | Current State | Required for 0.8 |
|---|---|---|
| Model identification | `ModelInfo` stored per observation | ✓ Sufficient |
| Input identification | SHA-256 of doc IDs + types + max tokens | ✗ Should hash actual content |
| Output identification | SHA-256 of raw API response | ✓ Sufficient |
| Prompt versioning | None | ✗ Needed |
| Deterministic replay | N/A (LLM calls are non-deterministic) | ✗ Cannot achieve; accept and document |

LLM-based observation generation is **inherently non-deterministic**. The
temperature is set to 0.3 (not 0), so identical inputs produce different outputs.
This violates CIVORA's reproducibility principle (Principle 8) for observations.
This must be accepted as a design constraint for 0.8 — observations are
advisory artifacts, not deterministic facts like rule evaluations.
