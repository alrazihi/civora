## 1. Context Architecture

### 1.1 Overview

The case context system assembles authorized, provenance-tracked facts from multiple domain sources into a single structured context object. AI receives only this assembled context — never direct database access.

```
┌─────────────────────────────────────────────────────────────────┐
│                        AI REQUEST                                │
│  (case_id, actor_id, options)                                   │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│                    AUTHORIZATION LAYER                          │
│  • Organization membership                                      │
│  • Case access (tenant isolation)                               │
│  • Person access                                                │
│  • Evidence access                                              │
│  • Document access                                              │
│  • Form submission access                                       │
│  • Rule evaluation access                                       │
│  • Decision access                                              │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│                    CONTEXT BUILDER                              │
│  • Case metadata                                                │
│  • Person information (where authorized)                        │
│  • Evidence (all / verified only)                               │
│  • Document content (where authorized)                          │
│  • Form submissions                                             │
│  • Rule evaluations                                             │
│  • Workflow instance + history                                  │
│  • Decisions                                                    │
│  • AI observations (pending/accepted)                           │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│                    CASE CONTEXT OUTPUT                          │
│  {                                                               │
│    "id": "uuid",                                                │
│    "organization_id": "uuid",                                   │
│    "case_id": "uuid",                                           │

│    "facts": [...],                                              │
│    "token_estimate": 4521,                                      │

│    }                                                            │
│  }                                                               │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 Domain Types (`internal/casecontext/domain/context.go`)

#### Fact Provenance (`FactProvenance`)
Every fact carries a provenance classification:

| Value | Description |
|-------|-------------|
| `SOURCE_FACT` | Direct from authoritative source (case record, person record, verified evidence) |
| `AI_OBSERVATION` | Generated by AI model, pending human review |
| `HUMAN_VERIFIED_FACT` | Verified by human reviewer (evidence verified, AI observation accepted) |
| `RULE_RESULT` | Output from deterministic rule engine evaluation |
| `HUMAN_DECISION` | Final decision by human decision-maker |
| `FORM_SUBMISSION` | Data submitted via forms |
| `WORKFLOW_HISTORY` | Workflow state transitions |

#### Fact Source Type (`FactSourceType`)
Identifies the originating domain entity:

| Value | Domain |
|-------|--------|
| `CASE_METADATA` | Case record |
| `PERSON` | Person record |
| `EVIDENCE` | Evidence record |
| `DOCUMENT` | Document content |
| `FORM_SUBMISSION` | Form submission data |
| `RULE_EVALUATION` | Rules engine output |
| `WORKFLOW_INSTANCE` | Current workflow state |
| `WORKFLOW_HISTORY` | Workflow transition history |
| `DECISION` | Decision record |
| `AI_OBSERVATION` | AI observation record |

#### Core Structures

```go
type Fact struct {
    ID           uuid.UUID      // Unique fact identifier
    CaseID       uuid.UUID      // Case this fact belongs to
    SourceType   FactSourceType // Originating domain
    SourceID     uuid.UUID      // Specific source record ID
    Provenance   FactProvenance // Classification
    Key          string         // Fact key (e.g., "case", "person", "evidence")
    Value        interface{}    // Fact payload
    ValueType    string         // "string" | "number" | "boolean" | "object" | "array" | "datetime"
    Confidence   *float64       // For AI observations (0.0-1.0)
    RetrievedAt  time.Time      // When fact was assembled
    ExpiresAt    *time.Time     // Optional TTL
    Metadata     map[string]any // Additional context
    References   []uuid.UUID    // Linked records (verifiers, related entities)
}

type CaseContext struct {
    ID              uuid.UUID
    OrganizationID  uuid.UUID
    CaseID          uuid.UUID
    ActorID         uuid.UUID
    Facts           []*Fact
    TokenEstimate   int
    CreatedAt       time.Time
    ExpiresAt       time.Time
    Authorization   AuthorizationMap
}

type AuthorizationEntry struct {
    ResourceType string
    ResourceIDs  []string
    Granted      bool
    Reason       string
}
```

### 1.3 Context Options (`ContextOptions`)

Controls what data sources are included:

```go
type ContextOptions struct {
    IncludeCaseMetadata     bool // Default: true
    IncludePerson           bool // Default: true
    IncludeEvidence         bool // Default: true
    IncludeVerifiedEvidence bool // Default: true
    IncludeDocuments        bool // Default: true
    IncludeFormSubmissions  bool // Default: true
    IncludeRuleEvaluations  bool // Default: true
    IncludeWorkflowHistory  bool // Default: true
    IncludeDecisions        bool // Default: true
    IncludeAIObservations   bool // Default: true
    MaxTokens               int  // Default: 8000
    MaxFacts                int  // Default: 200
    OnlyVerified            bool // Only VERIFIED evidence
    OnlyHumanVerified       bool // Only human-verified facts
}
```

## 2. Authorization Flow

### 2.1 Multi-Layer Authorization

Every data access passes through explicit authorization checks before inclusion:

```go
// 1. Organization membership (shared.UserChecker)
valid, err := s.userChecker.BelongsToOrganization(ctx, orgID, actorID)

// 2. Case access (tenant isolation)
canAccess, err := s.authChecker.CanAccessCase(ctx, orgID, caseID, actorID)

// 3. Per-resource authorization (each source type)
canAccess, err := s.authChecker.CanAccessPerson(ctx, orgID, personID, actorID)
canAccess, err := s.authChecker.CanAccessEvidence(ctx, orgID, evidenceID, actorID)
canAccess, err := s.authChecker.CanAccessDocument(ctx, orgID, documentID, actorID)
canAccess, err := s.authChecker.CanAccessFormSubmission(ctx, orgID, submissionID, actorID)
canAccess, err := s.authChecker.CanAccessRuleEvaluation(ctx, orgID, evaluationID, actorID)
canAccess, err := s.authChecker.CanAccessDecision(ctx, orgID, decisionID, actorID)
```

### 2.2 Cross-Tenant Attack Prevention

The authorization checker **must** enforce organization scoping at the database level. The `AuthorizationChecker` interface implementations use organization-scoped queries:

```sql
-- Example: Evidence access check
SELECT 1 FROM evidence 
WHERE id = $1 AND organization_id = $2 
AND EXISTS (
    SELECT 1 FROM service_requests sr
    JOIN cases c ON c.id = sr.case_id
    WHERE sr.id = evidence.service_request_id 
    AND c.organization_id = $2
    AND c.id = $3  -- case_id
)
```

### 2.3 Authorization Transparency

Every context includes an `AuthorizationMap` recording what was checked:

```json
{
  "authorization": {
    "case": {
      "resource_type": "case",
      "resource_ids": ["case-uuid"],
      "granted": true,
      "reason": "case found"
    },
    "person": {
      "resource_type": "person",
      "resource_ids": ["person-uuid"],
      "granted": false,
      "reason": "access denied"
    },
    "evidence": {
      "resource_type": "evidence",
      "resource_ids": ["ev-1", "ev-2"],
      "granted": true,
      "reason": "found 2 evidence items"
    }
  }
}
```

AI and human reviewers can audit what was accessible vs. denied.

## 3. Data Sources

### 3.1 Case Metadata (`CASE_METADATA`)

Always included when `IncludeCaseMetadata=true`. Provenance: `SOURCE_FACT`.

Fields: `id`, `case_number`, `title`, `description`, `status`, `workflow_state`, `service_type`, `priority`, `person_id`, `assigned_to_id`, `created_by_id`, timestamps, workflow links, `version`.

### 3.2 Person Information (`PERSON`)

Included when `IncludePerson=true` AND case has `PersonID` AND actor authorized. Provenance: `SOURCE_FACT` (or `HUMAN_VERIFIED_FACT` if verified separately).

Fields: `id`, `legal_name`, `date_of_birth`, `gender`, `nationality`, `address`, `phone`, `email`, `metadata`.

### 3.3 Evidence (`EVIDENCE`)

Included when `IncludeEvidence=true` or `IncludeVerifiedEvidence=true`. Filtered by `VerificationStatus` when `OnlyVerified=true`.

Provenance:
- `UNVERIFIED` → `SOURCE_FACT`
- `VERIFIED` → `HUMAN_VERIFIED_FACT`
- `NEEDS_REVIEW` / `REJECTED` → `SOURCE_FACT` (with status in payload)

Fields: `id`, `type`, `custom_type`, `description`, `source`, `metadata`, `verification_status`, `verified_by`, `verified_at`, `verification_reason`, `verification_method`, `person_id`, `uploaded_by`, `created_at`.

### 3.4 Document Content (`DOCUMENT`)

Included when `IncludeDocuments=true` AND `DocumentContentProvider` wired AND actor authorized for document. Content truncated to 2000 chars with `truncated` flag.

Provenance: `SOURCE_FACT` (or `HUMAN_VERIFIED_FACT` if parent evidence verified).

Fields: `id`, `evidence_id`, `file_name`, `content_type`, `size_bytes`, `checksum`, `storage_provider`, `content_preview`, `truncated`.

### 3.5 Form Submissions (`FORM_SUBMISSION`)

Included when `IncludeFormSubmissions=true`. Provenance: `FORM_SUBMISSION`.

Fields: `id`, `form_id`, `form_version_id`, `submitted_by`, `status`, `data`, `submitted_at`, `updated_at`.

### 3.6 Rule Evaluations (`RULE_EVALUATION`)

Included when `IncludeRuleEvaluations=true`. Provenance: `RULE_RESULT`.

Fields: `id`, `rule_set_id`, `rule_set_version`, `status`, `outcome`, `reason`, `matched_rule_id`, `trigger`, `evaluated_by`, `evaluated_at`, `facts_snapshot_keys`.

### 3.7 Workflow (`WORKFLOW_INSTANCE`, `WORKFLOW_HISTORY`)

Included when `IncludeWorkflowHistory=true`. Provenance: `SOURCE_FACT` (instance) / `WORKFLOW_HISTORY` (transitions).

Instance fields: `id`, `workflow_def_id`, `workflow_def_version`, `current_state`, `started_at`, `completed_at`, `metadata`, `version`.

History fields: `id`, `from_state`, `to_state`, `transition_key`, `actor_id`, `occurred_at`, `reason`, `metadata`, `decision_id`.

### 3.8 Decisions (`DECISION`)

Included when `IncludeDecisions=true`. Provenance: `HUMAN_DECISION`.

Fields: `id`, `decision`, `reason`, `decision_maker`, `decided_at`, `workflow_state`, `rule_evaluation_ids`, `evidence_ids`, `form_submission_id`, `review_queue_entry_id`, `version`, `superseded_by_id`.

### 3.9 AI Observations (`AI_OBSERVATION`)

Included when `IncludeAIObservations=true`. Filtered by `OnlyHumanVerified`.

Provenance:
- `PENDING_REVIEW` → `AI_OBSERVATION`
- `ACCEPTED` → `HUMAN_VERIFIED_FACT`
- `REJECTED` → `AI_OBSERVATION` (with status in payload)

Fields: `id`, `evidence_id`, `type`, `source`, `status`, `content`, `confidence`, `input_hash`, `output_hash`, `model`, `created_at`, `created_by`, `reviewed_at`, `reviewed_by`, `review_notes`.

## 4. Provenance & Grounding

### 4.1 Provenance Chain

Each fact maintains a complete chain from source to AI:

```
AI Observation (provenance: AI_OBSERVATION)
    ↓ references
Evidence Record (provenance: HUMAN_VERIFIED_FACT)
    ↓ verified_by
Human Verifier (user_id)
    ↓
VerificationRecord (audit trail)
```

### 4.2 Reference Tracking

Facts include `References` array linking to:
- Human verifiers (`verified_by`, `reviewed_by`)
- Decision makers (`decision_maker`)
- Rule evaluation IDs
- Workflow transition actors
- Superseded decisions

### 4.3 Fact Identity & Reproducibility

- Every fact has unique `ID` (UUID v4)
- `InputHash` / `OutputHash` on AI observations for reproducibility
- `RetrievedAt` timestamp for freshness
- `ExpiresAt` for TTL (default 1 hour)

### 4.4 Distinguishing Fact Types

The system enforces clear distinctions:

| Category | Provenance | Human Review Required | Example |
|----------|------------|----------------------|---------|
| Source Fact | `SOURCE_FACT` | No | Case title, person name, verified evidence |
| AI Observation | `AI_OBSERVATION` | Yes | Entity extraction, summary, classification |
| Human Verified | `HUMAN_VERIFIED_FACT` | Yes (already done) | Verified evidence, accepted AI observation |
| Rule Result | `RULE_RESULT` | No (deterministic) | Eligibility outcome, score |
| Human Decision | `HUMAN_DECISION` | Yes (the decision itself) | Approve/Reject/Escalate |

### 6.1 Test Coverage (`internal/casecontext/application/service_test.go`)

| Test | Purpose |
|------|---------|
| `TestBuildContext_Success` | Basic context assembly with all defaults |
| `TestBuildContext_ActorNotInOrg` | Rejects actors not in organization |
| `TestBuildContext_CaseAccessDenied` | Blocks access to other tenant's cases |
| `TestBuildContext_NilActorID` | Requires valid actor |
| `TestBuildContext_WithPerson` | Includes person when authorized |
| `TestBuildContext_WithEvidence` | Includes evidence with correct provenance |
| `TestBuildContext_OnlyVerifiedEvidence` | Filters to VERIFIED only |
| `TestBuildContext_PersonAccessDenied` | Silently omits person when unauthorized |

### 6.2 Attack Scenarios Covered

1. **Cross-tenant case access**: `CanAccessCase` checks organization ID match
2. **Cross-tenant evidence access**: Evidence queries scoped to organization
3. **Unauthorized document access**: `CanAccessDocument` required before content retrieval
4. **Person PII exposure**: `CanAccessPerson` gate before inclusion
5. **Context injection**: All inputs validated, context built server-side only
6. **Token exhaustion**: `MaxTokens` / `MaxFacts` limits enforced in builder

### 6.3 Integration Test Requirements

Run with database (`go test -p 1 -count=1 ./...`):

- Multi-tenant database with org A and org B
- Actor from org A attempts to build context for org B's case → **403 Forbidden**
- Actor from org A attempts to access org B's evidence → **Excluded silently**
- Actor without person access → Person fact omitted, authorization map records denial

## 7. Limitations

### 7.1 Current Constraints

1. **No streaming / incremental context**: Entire context assembled in one call
2. **Document content size**: Limited to 100KB per document, 2KB preview in context
3. **No real-time updates**: Context expires after 1 hour, must rebuild
4. **No cross-case context**: Single case per context request
5. **AuthorizationChecker not implemented**: Interface defined, wiring required per deployment

### 7.2 Future Enhancements

- [ ] Streaming context for large cases
- [ ] Vector search integration for evidence retrieval
- [ ] Context versioning / diff
- [ ] Fine-grained field-level PII redaction
- [ ] Webhook notifications on context rebuild
- [ ] AuthorizationChecker default implementation using existing RBAC
