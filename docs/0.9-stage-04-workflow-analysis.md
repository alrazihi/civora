# Stage 4: Bottleneck & Workflow Analysis

## Goal

Add a read-only workflow analysis module that surfaces neutral, data-driven observations about case flow, state accumulation, duration anomalies, closure patterns, information request frequency, review backlog, and threshold exceedances.

All analysis is derived from real API queries against live data. No hardcoded demo data is used in production code.

## Neutral Language

Observations use neutral, descriptive language only:

- `high_volume` — indicates higher-than-threshold case volume in a state
- `longer_duration` — indicates observed duration exceeds configured threshold
- `increased_backlog` — indicates pending review count exceeds threshold
- `higher_frequency` — indicates information request frequency exceeds threshold

The system never recommends or auto-applies workflow changes, rule changes, approval changes, or assignment changes.

## Configurable Thresholds

Thresholds are explicit and configurable via query parameters on the analysis endpoint:

| Parameter | Type | Default | Description |
|---|---|---|---|
| `state_accumulation_threshold` | integer | 10 | Minimum case count to flag state accumulation |
| `state_duration_threshold_hours` | float | 24 | Hours threshold for state duration anomalies |
| `aging_threshold_hours` | float | 720 | Hours threshold for aging cases |
| `review_backlog_threshold` | integer | 20 | Minimum pending reviews to flag backlog |
| `info_request_frequency_per_case` | float | 1.5 | Information request frequency per case threshold |
| `cycle_time_threshold_hours` | float | 72 | Hours threshold for case cycle time |

A `GET /metrics/analysis/thresholds` endpoint returns the defaults.

## Backend Changes

### Domain

`internal/operations/domain/analysis.go`

- `AnalysisThresholds` struct with all six threshold fields
- `DefaultAnalysisThresholds` var with sensible defaults
- `WorkflowAnalysisReport` struct containing six observation slices
- Six observation structs: `StateAccumulationObservation`, `StateDurationAnomaly`, `WorkflowClosurePattern`, `InformationRequestPattern`, `ReviewBacklogObservation`, `ThresholdExceedanceObservation`
- `AnalysisRepository` interface with seven methods
- `AnalysisService` interface

### Application

`internal/operations/application/analysis_service.go`

- `AnalysisService` with `GetWorkflowAnalysisReport` orchestration
- Fills missing thresholds with `DefaultAnalysisThresholds`
- Delegates to repository and stamps `CalculatedAt`

### Infrastructure

`internal/operations/infrastructure/postgres/analysis_repository.go`

- All six analysis queries on `PostgresMetricsRepository`
- `GetWorkflowAnalysisReport` aggregates all six observation types

### API

`internal/operations/api/analysis_handler.go`

- `AnalysisHandler` with `RegisterRoutes`
- `GET /organizations/{orgId}/operations/analysis/workflow` — returns `WorkflowAnalysisReport`
- `GET /organizations/{orgId}/operations/analysis/thresholds` — returns `AnalysisThresholds`
- Query parameters allow overriding each threshold

- Instantiates `AnalysisService` and `AnalysisHandler`

## Notes

- The analysis module is strictly observational. It does not modify workflows, rules, approvals, or assignments.
- All threshold defaults are defined in `domain.DefaultAnalysisThresholds` and can be overridden per request.
- The frontend uses the existing vanilla JS pattern with hash routing and no new frameworks.
