**Date**: 2026-09-20
**Branch**: main
**Commit**: HEAD
**Reviewer**: Kilo / Pre-1.0 Verification Stage

## 1. Executive Summary

Stage 2 verified transport security. Stage 3 addresses five confirmed
security and business-logic defects identified in the 0.9.5 verification
report:

1. **Login enumeration** — invalid credentials and nonexistent accounts were
   distinguishable via timing and rate-limit behavior.
2. **Evidence verification replay** — no state-machine enforcement allowed
   semantically invalid repeated transitions.
3. **Decision supersede** — a self-referential `SupersededByID` bug and a
   database unique constraint conflicted with versioned decision history.
4. **Database defaults** — production-looking default credentials (`civora` /
   `civora`) were used when environment variables were unset.
5. **AI audit error swallowing** — provider-failure audit errors were silently
   discarded.

All defects are resolved. Regression tests are added. The complete relevant
test suite passes.

## 2. Login Enumeration

### 2.1 Finding

`internal/identity/application/service.go` — `Authenticate` skipped bcrypt
verification when the user did not exist, creating a measurable timing
difference between "user not found" and "wrong password". Additionally, the
login rate-limit response contained the message *"Account temporarily locked
due to too many failed login attempts"*, implying account existence.

### 2.2 Fix

**Timing-safe authentication** (`internal/identity/application/service.go`):

```go
const timingSafeDummyHash = "$2a$10$dummy.hash.for.timing.safety.only.aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"

func (s *IdentityService) Authenticate(ctx context.Context, params AuthenticateParams) (*AuthenticateResult, error) {
    // ...
    user, err := s.userRepo.FindByEmail(ctx, params.OrganizationID, params.Email)
    if err != nil {
        s.hasher.Verify(params.Password, timingSafeDummyHash)
        return nil, ErrInvalidCredentials
    }
    if user.PasswordHash == nil || *user.PasswordHash == "" {
        s.hasher.Verify(params.Password, timingSafeDummyHash)
        return nil, ErrInvalidCredentials
    }
    // ...
}
```

A dummy bcrypt comparison is performed for non-existent users so that the
response time is dominated by hashing, not by database lookup.

**Generic rate-limit messages** (`internal/identity/api/handler.go`):

- Login: `"Too many attempts. Try again in %d seconds."` (code: `RATE_LIMITED`)
- Registration: `"Too many attempts. Try again in %d seconds."` (code: `RATE_LIMITED`)

Neither message references accounts, emails, or login status.

### 2.3 Tests Added

| File | Test | Description |
|------|------|-------------|
| `internal/identity/application/service_test.go` | `TestAuthenticate_NonExistentUserReturnsInvalidCredentials` | Non-existent user returns `ErrInvalidCredentials` |
| `internal/identity/application/service_test.go` | `TestAuthenticate_InvalidPasswordReturnsInvalidCredentials` | Wrong password returns `ErrInvalidCredentials` |
| `internal/identity/api/handler_test.go` | `TestLogin_NonExistentUserReturnsSameErrorAsInvalidCredentials` | HTTP 401 with identical message for both cases |
| `internal/identity/api/handler_test.go` | `TestLogin_RateLimitMessageDoesNotLeakAccountExistence` | Rate-limit response omits account/email/locked keywords |

### 2.4 Security Guarantees

- Invalid credentials and nonexistent accounts produce identical HTTP status,
  body, and timing characteristics.
- Rate limiting applies uniformly regardless of account existence.
- Internal audit logging (`auth.failed`) preserves the user ID when available
  for operational debugging without exposing it to the client.

## 3. Evidence Verification Replay

### 3.1 Finding

`internal/evidence/domain/evidence.go` — `applyVerification` allowed any
status transition without validation. This permitted semantically invalid
replays such as `VERIFIED → VERIFIED` or `REJECTED → REJECTED`.

### 3.2 Intended Lifecycle

```
UNVERIFIED → VERIFIED
UNVERIFIED → REJECTED
UNVERIFIED → NEEDS_REVIEW
NEEDS_REVIEW → VERIFIED
NEEDS_REVIEW → REJECTED
VERIFIED → REJECTED      (correction after review)
VERIFIED → NEEDS_REVIEW  (escalation after review)
REJECTED → VERIFIED      (correction accepted)
REJECTED → NEEDS_REVIEW  (escalation after rejection)
```

Same-state transitions (e.g. `VERIFIED → VERIFIED`, `REJECTED → REJECTED`)
are rejected to prevent replay attacks while preserving legitimate correction
and review workflows.

### 3.3 Fix

```go
func isValidVerificationTransition(from, to VerificationStatus) bool {
    switch from {
    case VerificationStatusUnverified:
        return to == VerificationStatusVerified || to == VerificationStatusRejected || to == VerificationStatusNeedsReview
    case VerificationStatusNeedsReview:
        return to == VerificationStatusVerified || to == VerificationStatusRejected
    case VerificationStatusVerified:
        return to == VerificationStatusRejected || to == VerificationStatusNeedsReview
    case VerificationStatusRejected:
        return to == VerificationStatusVerified || to == VerificationStatusNeedsReview
    default:
        return false
    }
}
```

`applyVerification` now calls `isValidVerificationTransition` before mutating
state. History remains fully auditable via `VerificationRecord` entries.

### 3.4 Tests Added

| File | Test | Description |
|------|------|-------------|
| `internal/evidence/domain/evidence_test.go` | `TestEvidence_VerificationStateTransitions/verify_then_verify_is_rejected` | Same-state VERIFIED→VERIFIED rejected |
| `internal/evidence/domain/evidence_test.go` | `TestEvidence_VerificationStateTransitions/reject_then_reject_is_rejected` | Same-state REJECTED→REJECTED rejected |
| `internal/evidence/domain/evidence_test.go` | `TestEvidence_VerificationStateTransitions/verified_to_needs_review_is_allowed` | VERIFIED→NEEDS_REVIEW allowed |
| `internal/evidence/domain/evidence_test.go` | `TestEvidence_VerificationStateTransitions/rejected_to_needs_review_is_allowed` | REJECTED→NEEDS_REVIEW allowed |
| `internal/evidence/application/service_test.go` | `TestVerifyEvidence_ReplayAfterVerifiedIsRejected` | Re-verification after VERIFIED returns error |
| `internal/evidence/application/service_test.go` | `TestRejectEvidence_ReplayAfterRejectedIsRejected` | Re-rejection after REJECTED returns error |
| `internal/evidence/application/service_test.go` | `TestMarkEvidenceForReview_ReplayAfterNeedsReviewIsRejected` | Re-review after NEEDS_REVIEW returns error |

### 3.5 Concurrency & Replay

The state-machine check is performed in-memory on the domain object before
the transaction commits. Concurrent requests for the same evidence will
serialize at the database row level; the second transaction will observe the
updated status and reject the invalid transition.

## 4. Decision Supersede

### 4.1 Finding

Two conflicts existed:

1. **Self-referential `SupersededByID`**: `NewSupersedingDecision` set
   `d.SupersededByID = &d.ID`, making the new decision claim it superseded
   itself.
2. **Unique constraint conflict**: Migration `0006` created a unique index on
   `(organization_id, service_request_id)`, preventing versioned decisions
   from coexisting.

### 4.2 Intended Decision Model

Decisions are versioned. A service request may have multiple decisions over
time, each with an incrementing `version`. The latest version is the active
decision. The previous version's `superseded_by_id` points to the new
decision's ID.

### 4.3 Fix

**Domain** (`internal/decisions/domain/decision.go`):

```go
func NewSupersedingDecision(...) (*Decision, error) {
    version := 1
    if supersededDecision != nil {
        version = supersededDecision.Version + 1
    }
    d, err := NewDecisionWithContext(..., version)
    if err != nil {
        return nil, err
    }
    // The new decision is current; SupersededByID is nil.
    return d, nil
}
```

**Application service** (`internal/decisions/application/service.go`):

```go
err = database.InTransaction(ctx, s.repo.DB(), func(tx *sql.Tx) error {
    existing.SupersededByID = &d.ID
    if err := s.repo.UpdateTx(ctx, tx, existing); err != nil {
        return fmt.Errorf("failed to update superseded decision: %w", err)
    }
    if err := s.repo.SaveTx(ctx, tx, d); err != nil {
        return fmt.Errorf("failed to save superseding decision: %w", err)
    }
    // ...
})
```

**Repository** (`internal/decisions/infrastructure/postgres/decision_repository.go`):
Added `UpdateTx` to update the `superseded_by_id` of the previous decision.

**Migration** (`migrations/0006_decision_uniqueness.up.sql`):

```sql
CREATE UNIQUE INDEX idx_decisions_service_request_version_unique
    ON decisions (organization_id, service_request_id, version);
```

This allows multiple versions per service request while preventing duplicate
versions.

### 4.4 Tests Added

| File | Test | Description |
|------|------|-------------|
| `internal/decisions/domain/decision_test.go` | `TestNewSupersedingDecision` | New decision has `SupersededByID == nil` |
| `internal/decisions/application/service_test.go` | `TestSupersedeDecision_CreatesNewVersion` | Old decision's `SupersededByID` points to new decision |
| `internal/decisions/application/service_test.go` | `TestSupersedeDecision_NoExistingDecision` | Superseding without existing decision fails |

### 4.5 Invariants

- A decision never points to itself.
- Multiple supersessions are supported (version increments each time).
- History is fully auditable via `GetDecisionHistory`.
- Uniqueness is enforced at the `(org, service_request, version)` level.
- The transaction updates the old decision and inserts the new one atomically.

## 5. Database Defaults

### 5.1 Finding

`internal/config/config.go` used hardcoded defaults `civora` / `civora` for
`CIVORA_DB_USER`, `CIVORA_DB_PASSWORD`, and `CIVORA_DB_NAME`, and `disable`
for `CIVORA_DB_SSLMODE`. Deployments that omitted these variables would
connect with well-known credentials over an unencrypted connection.

### 5.2 Fix

Production mode (`CIVORA_ENV=production`) now requires explicit database
credentials:

```go
if os.Getenv("CIVORA_ENV") == "production" {
    if cfg.Database.User == "" {
        return nil, fmt.Errorf("CIVORA_DB_USER must be set in production")
    }
    if cfg.Database.Password == "" {
        return nil, fmt.Errorf("CIVORA_DB_PASSWORD must be set in production")
    }
    if cfg.Database.DBName == "" {
        return nil, fmt.Errorf("CIVORA_DB_NAME must be set in production")
    }
    if cfg.Auth.JWTSecret == "dev-secret-change-me-32-chars-minimum" {
        return nil, fmt.Errorf("CIVORA_AUTH_JWT_SECRET must be changed in production")
    }
}
```

Development convenience is preserved:

| Variable | Development Default | Production Requirement |
|----------|---------------------|------------------------|
| `CIVORA_DB_USER` | `civora` | **Must be set explicitly** |
| `CIVORA_DB_PASSWORD` | `civora` | **Must be set explicitly** |
| `CIVORA_DB_NAME` | `civora` | **Must be set explicitly** |
| `CIVORA_DB_SSLMODE` | `disable` | Defaults to `require` in production |

### 5.3 Deployment Guidance

Production deployments must supply all database credentials via environment
variables or a secrets manager. The `.env` file is **not** loaded in
production (`CIVORA_ENV=production`).

Example production environment:

```bash
CIVORA_ENV=production
CIVORA_DB_HOST=db.internal.example.com
CIVORA_DB_PORT=5432
CIVORA_DB_USER=civora_prod
CIVORA_DB_PASSWORD=<from-vault-or-env>
CIVORA_DB_NAME=civora_prod
CIVORA_DB_SSLMODE=require
CIVORA_AUTH_JWT_SECRET=<from-vault-or-env>
```

## 6. AI Audit Error Handling

### 6.1 Finding

`internal/ai/application/service.go` — `recordAudit` silently discarded
errors from the audit event recorder using `_ = s.auditor.RecordEvent(...)`.
In the provider-failure path, this meant AI audit failures were invisible.

### 6.2 Fix

```go
func (s *AIService) recordAudit(ctx context.Context, ...) {
    if s.auditor == nil {
        return
    }
    if err := s.auditor.RecordEvent(ctx, auditdomain.RecordEventParams{
        // ...
    }); err != nil {
        log.Printf("failed to record audit event %s for %s %s: %v",
            action, resource, *resourceID, err)
    }
}
```

The audit error is now logged with full context. Transactional audit paths
(`RecordEventInTx`) already returned errors correctly; this change only
affects the non-transactional `recordAudit` helper used in provider-failure
paths.

|------|------|-------------|
| `internal/ai/application/service_test.go` | `TestAIService_GenerateObservations_ProviderErrorWithAuditFailure` | Provider failure returns `ErrAIProviderUnavailable` even when audit recorder also fails |
