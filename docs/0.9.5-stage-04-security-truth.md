# CIVORA 0.9.5 — Stage 4: Security Truth Documentation

> **Status**: Implemented
> This document provides an honest accounting of CIVORA's security
> posture, what the application provides, what operators must provide,
> and known limitations. It is intended to prevent overclaiming and to
> give operators the information they need to make informed deployment
> decisions.

---

## 1. Security provided by CIVORA

The following security controls are implemented in the application
code and are present in every deployment:

- **Authentication**: Bearer-token authentication on every request.
  Tokens are short-lived (24h).
- **Authorization**: Role-based authorization checked at the service
  and data layers. No client-side trust in role claims.
- **Tenant isolation**: All data is scoped by `organization_id`.
  Queries are filtered at the data-access layer. Foreign keys enforce
  ownership.
- **Input validation**: All input is validated and sanitized at API
  boundaries. No execution of arbitrary code from user-supplied data
  (including workflow definitions).
- **Secrets handling**: Secrets are never logged. Passwords are hashed
  using bcrypt. Rate limiting is enforced on authentication endpoints.
- **Timing-safe auth**: Login attempts use timing-safe dummy bcrypt
  comparison to prevent user-enumeration via response-time side
  channels.
- **Generic error messages**: Authentication failures return
  `RATE_LIMITED` or `INVALID_CREDENTIALS` without revealing whether a
  username exists.
- **Evidence state machine**: Evidence items can only transition
  through `PENDING → VERIFIED → REJECTED`. Re-verification and
  backward transitions are prevented.
- **Decision supersession integrity**: Superseding decisions are
  versioned and linked to the previous decision via `SupersededByID`
  on the old record. The old decision is never mutated.
- **AI module isolation**: AI observation assistance is architecturally
  isolated from consequential system functions. There is no code path
  from AI outputs to decisions, workflow transitions, rule evaluation
  results, form submission data, evidence modification, or case status
  changes. AI outputs require explicit human review before any
  downstream use.
- **Audit trail**: A tamper-evident, hash-chained audit trail
  (SHA-256) stored in a dedicated `audit` schema. Audit writes occur
  in the same transaction as the state change they record. The server
  verifies hash chains on startup and on background ticks.
- **Transport security**: CIVORA supports reverse-proxy TLS
  termination and direct TLS termination. HSTS is emitted when the
  deployment is actually HTTPS. Forwarded headers are only trusted
  from explicitly configured proxy IPs.

## 2. Deployment responsibilities

The following are **not** provided by CIVORA and are the operator's
responsibility:

- **TLS certificate management**: When using direct TLS termination,
  operators must provide and rotate `CIVORA_SERVER_TLS_CERT` and
  `CIVORA_SERVER_TLS_KEY`.
- **Reverse-proxy configuration**: When using a reverse proxy,
  operators must configure `CIVORA_SERVER_TRUSTED_PROXIES` and ensure
  the proxy sets `X-Forwarded-Proto: https` and `X-Forwarded-For` on
  every request.
- **Database backups**: Operators must configure PostgreSQL backups
  (e.g., `pg_dump`, continuous archiving, or managed snapshots) and
  test restore procedures.
- **Disaster recovery**: Operators must define recovery time
  objectives (RTO) and recovery point objectives (RPO).
- **Secrets management**: Operators must manage and rotate database
  credentials, JWT signing keys, and AI provider keys.
- **Network security**: Operators must configure firewalls, DDoS
  protection, and host hardening.
- **Observability**: Operators must configure log aggregation,
  monitoring, and alerting.
- **Compliance procedures**: Operators must establish data retention
  policies, access reviews, incident response plans, and any other
  procedures required by their regulatory environment.

## 3. Known limitations

### 3.1 Not production-ready

CIVORA is in early development (Milestones 0.x). It is not yet
production-ready. Operators should not deploy it in production
environments without independent security review and operational
safeguards.

### 3.2 No encryption at rest

PostgreSQL data is stored unencrypted by default. Operators should
rely on PostgreSQL-level encryption (e.g., tablespace encryption) or
filesystem/disk-level encryption if required. No KMS integration is
provided.

### 3.3 No built-in backup/DR

CIVORA does not include built-in backup or disaster-recovery
functionality. Operators are responsible for configuring PostgreSQL
backups and testing restores.

### 3.4 No GDPR data export/deletion APIs

Bulk data-export and per-user deletion endpoints are not implemented.
Operators who need to fulfill GDPR data-subject requests must do so
through direct database access or by implementing custom export/deletion
workflows.

### 3.5 No SOC 2 / HIPAA controls

CIVORA does not implement SOC 2 Trust Services Criteria or HIPAA
technical safeguards (e.g., access reviews, change management, encryption
at rest). Compliance with these frameworks depends on the operator's
deployment configuration, policies, and controls.

### 3.6 Audit trail limitations

The hash chain detects accidental or offline tampering, but:

- A compromised application process can write a valid chain with false
  contents.
- A database administrator with write access can modify audit rows and
  recompute the chain consistently.
- There is no external anchor (e.g., blockchain, WORM storage, or
  external witness).
- Audit events are not stored in a separate database instance; they
  share the same PostgreSQL instance as business data, though they live
  in a dedicated `audit` schema.

### 3.7 JWT non-revocable

JWT tokens are short-lived (24h) but cannot be revoked before expiry.
A logout/revocation endpoint is planned for a future milestone.

### 3.8 AI module limitations

- AI providers (OpenAI, Local/Ollama, Noop) are optional and off by
  default via `CIVORA_AI_ENABLED` (default off).
- AI outputs are advisory only and require explicit human review.
- AI prompts and outputs may contain sensitive data; operators must
  ensure their AI provider agreements and data-handling policies are
  compatible with their regulatory requirements.
- There is no prompt-injection defense against adversarially crafted
  evidence documents; the prompt-injection guard operates on the
  structured observation input, not on raw document content.

## 4. Compliance posture

CIVORA does **not** claim compliance with any regulatory framework,
including but not limited to:

- GDPR
- HIPAA
- SOC 2
- PCI DSS
- WCAG 2.1 (accessibility)
- Any other industry-specific or regional regulation

Operators are responsible for:

- Conducting their own risk assessments.
- Configuring CIVORA and their infrastructure to meet their regulatory
  requirements.
- Establishing policies, procedures, and controls appropriate to their
  environment.
- Engaging independent auditors if compliance certification is
  required.

CIVORA provides **application-level controls** for tenant isolation,
audit trail integrity, and human-in-the-loop decision making. These
controls may support an operator's compliance efforts, but they do not
by themselves constitute compliance.
