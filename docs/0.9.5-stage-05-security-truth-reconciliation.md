## Summary

### 1. Security claims verified
All 27 security claims were verified against source code, tests, configuration, and migrations at HEAD `20c3de4576d375d3e857e7a15f23185b98ac0979`.

### 2. Claims corrected
Two corrections were applied to Stage 4:
- **JWT reuse detection** (line 152-153): Changed from "but reuse detection... is not enforced" to clarify that reuse detection works via the hash mismatch when a rotated token is reused.
- **Authorization on refresh** (line 24-28): Added clarification that roles are re-fetched from the database on token refresh.
- **Decision uniqueness** (line 184-190): Corrected to reflect the database unique constraint on `(organization_id, service_request_id, version)`.

### 3. Claims requiring code changes
None. All security controls are properly implemented.

### 4. Remaining 1.0 blockers
- **Evidence concurrent verification** (§3.10): No row-level lock; lost updates possible under concurrent verification. Consider adding `SELECT ... FOR UPDATE`.
- **Session repository tenant filters** (§3.9): Documented limitation. Mitigated by UUID-random tokens and middleware validation, but defense-in-depth would require adding `organization_id` to session lookups.

### 5. Deployment responsibilities
Operators are responsible for:
- TLS certificate management (direct TLS)
- Reverse-proxy configuration and `CIVORA_SERVER_TRUSTED_PROXIES`
- PostgreSQL backups and DR
- Secrets management (DB credentials, JWT signing keys, AI provider keys)
- Network security (firewalls, DDoS, host hardening)
- Observability (logging, monitoring, alerting)
- Compliance procedures (data retention, access reviews, incident response)
- Encryption at rest (tablespace or disk-level)
- WAF / perimeter security
