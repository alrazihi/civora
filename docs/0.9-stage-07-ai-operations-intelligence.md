## 2. Goal

Add an **AI-assisted Operations Intelligence** layer that reuses the existing
0.8 provider abstraction and grounding architecture.

The AI may:
- summarize operational trends
- explain observed bottlenecks
- summarize workload
- identify unusual patterns
- answer questions about authorized metrics
- suggest questions for an administrator
- explain changes over time

The AI **must not**:
- invent metrics
- alter metrics
- alter workflows
- modify rules
- approve/reject cases
- reassign cases automatically
- expose unauthorized tenant data
- present speculation as fact

Every AI statement must be grounded in actual CIVORA metrics/data.

## 3. Architecture

The AI Operations Intelligence layer follows the existing modular-monolith /
clean-architecture convention:

```
                  ┌───────────────────────────┐
    domain  ◄─────│  IntelligenceRequest      │      (pure, no I/O)
                  │  IntelligenceResponse     │
                  │  IntelligenceProvider     │
                  │  ChatRequest/ChatResponse │
                  └───────────▲──────────────┘
                              │ uses
                  ┌───────────┴───────────┐
    application ◄─│ OperationsIntelligence │  Application service
                  │   Service              │  (orchestration + grounding)
                  └───────────▲───────────┘
                              │ calls
    infrastructure             │
    ┌──────────────────────────┴──────────────────────────┐
    │ providers/                                          │
    │  openai.go / local.go / noop.go  (existing 0.8)     │
    └──────────────────────────────────────────────────────┘
```

Key properties:
- The domain layer defines `IntelligenceProvider`, which reuses the
  `application.ChatRequest` / `application.ChatResponse` contract already
  established in `internal/ai/application`.
- The application service builds a **grounded prompt** from actual metrics,
  workflow analysis, and impact intelligence data before calling the provider.
- The handler enforces tenant scoping and role checks (`admin`, `staff`).
- The AI layer is **read-only**: it never writes cases, workflows, or rules.

## 5. Grounding architecture

The application service builds a system prompt that explicitly instructs the
model to:
- use **only** the provided metrics data
- not invent metrics or alter workflows
- say so explicitly when data is insufficient

It then fetches:
1. **Operations metrics** via `operationsService.GetAllMetrics`
2. **Workflow analysis** via `analysisService.GetWorkflowAnalysisReport`
3. **Impact intelligence** via `impactService.GetImpactIntelligenceReport`

Each data source is appended to the prompt as JSON. If a source is
unavailable, the prompt records `"error": "<source> unavailable"` rather than
fabricating data.

The resulting `IntelligenceResponse` includes:
- `Summary`: the AI-generated text
- `Details`: provenance metadata for each data source included
- `Model`: provider/model metadata
- `GeneratedAt`: timestamp

## 6. Safety boundaries

| Constraint | Enforcement |
|---|---|
| No metric invention | System prompt explicitly forbids it; only real metric data is injected |
| No workflow/rule modification | AI layer has no write access to workflows or rules |
| No case actions | AI layer does not call approval, assignment, or transition APIs |
| Tenant isolation | Handler uses `RequireSameTenant` + `RequireAnyRole("admin", "staff")` |
| Read-only | `OperationsIntelligenceService` has no repository write methods |
| Insufficient data handling | System prompt instructs model to say so explicitly |

The AI layer is **advisory only**. It returns text; the human administrator
decides what to do with it.

## 7. Provider reuse

The existing 0.8 providers are extended with one new method:

```go
type AIProvider interface {
    GenerateObservations(ctx context.Context, req ProviderRequest) ([]ObservationResult, error)
    GenerateChatCompletion(ctx context.Context, req ChatRequest) (*ChatResponse, error)
    ProviderInfo() domain.ModelInfo
}
```

Implementations:
- `OpenAIProvider.GenerateChatCompletion` — calls `POST /chat/completions`,
  validates response with `PromptInjectionGuard`, returns `ChatResponse`
- `LocalProvider.GenerateChatCompletion` — delegates to embedded
  `OpenAIProvider`, overrides provider metadata to `"local"`
- `NoopProvider.GenerateChatCompletion` — returns `ErrProviderDisabled`

Prompt injection guards continue to run inside the provider before any
response is returned to the application layer.

## 8. Configuration

No new environment variables are required. The operations intelligence layer
uses the existing AI configuration:

| Variable | Default | Notes |
|---|---|---|
| `CIVORA_AI_ENABLED` | `false` | Gates all AI |
| `CIVORA_AI_PROVIDER` | `"noop"` | `noop` / `openai` / `local` |
| `CIVORA_AI_OPENAI_API_KEY` | `""` | Required for hosted OpenAI |
| `CIVORA_AI_OPENAI_MODEL` | `gpt-4o-mini` | Hosted model |
| `CIVORA_AI_LOCAL_ENABLED` | `false` | Required for `"local"` |
| `CIVORA_AI_LOCAL_BASE_URL` | `http://localhost:11434/v1` | Local LLM URL |
| `CIVORA_AI_LOCAL_MODEL` | `"llama3"` | Local model name |

When AI is disabled or unconfigured, the `NoopProvider` returns
`ErrProviderDisabled`, which the handler maps to HTTP 503.

## 9. Routes

```
POST /api/v1/organizations/{orgId}/operations/intelligence?type={type}&question={question}&period={period}&bucket={bucket}&workflow_key={key}&status={status}
GET  /api/v1/organizations/{orgId}/operations/intelligence/suggested-questions
```

Both routes require authentication, `RequireSameTenant`, and role
`admin` or `staff`.

Query parameters:
- `type` — one of the `IntelligenceRequestType` values; defaults to
  `summarize_trends`
- `question` — free-text question for `answer_question` type
- `period` — metric period (`daily`, `weekly`, `monthly`); defaults to `daily`
- `bucket` — RFC3339 timestamp; defaults to now
- `workflow_key` — optional workflow filter
- `status` — optional status filter

## 10. Failure behavior

| Failure | Behavior |
|---|---|
| AI provider disabled / noop | HTTP 503; message: "AI provider is not configured or is disabled" |
| Provider unavailable | HTTP 500; message: "failed to generate intelligence" |
| Metrics unavailable | Prompt records error for that source; AI may still answer from other sources or say data is insufficient |
| Invalid request | HTTP 400 |

AI failure **never**:
- alters metrics
- modifies workflows or rules
- approves/rejects cases
- exposes data from another tenant

## 11. Distinguishing statement types

Every response is structured so the client can distinguish:

| Field | Meaning |
|---|---|
| `summary` | AI interpretation of the grounded data |
| `details` | Provenance metadata: which data sources were included, their source service, and confidence |
| `model` | Provider/model metadata |
| `generated_at` | When the response was produced |

Clients should render AI interpretations with appropriate caveats, and
should surface `details` so administrators can see which metrics the AI used.

## 15. Verdict

**GO**

The AI-assisted Operations Intelligence layer is implemented on top of the
existing 0.8 provider abstraction. It is read-only, tenant-scoped, role-gated,
and explicitly instructs the model to use only provided metrics data. The
provider interface is extended with a single new method that all existing
providers implement. Failure behavior is safe: the noop provider returns 503,
and provider errors never alter case data, workflows, or rules.
