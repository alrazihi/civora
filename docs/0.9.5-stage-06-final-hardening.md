## Original Problem

The previous session repository changes (introduced in the working tree prior to this stage) incorrectly assumed that `organization_id` is available in every repository call. This broke legitimate authentication flows where tenant context is not established until after the initial lookup — most critically the refresh-token flow, where only the refresh-token hash is known at lookup time.

## Why the Previous Repository Approach Was Incorrect

The previous approach added `organization_id uuid.UUID` as a required parameter to every session repository method:

- `FindByID(ctx, sessionID, organizationID)`
- `FindActiveByUserID(ctx, userID, organizationID)`
- `Revoke(ctx, sessionID, organizationID)`
- `RevokeAllByUserID(ctx, userID, organizationID)`
- `MarkUsed(ctx, sessionID, organizationID)`

This created a hard dependency on organization context that does not exist during:
1. **Refresh-token lookup** — only the hash is known; organization_id is retrieved from the session after lookup.
2. **Pre-authentication flows** — the session is looked up before the JWT claims (including organization_id) are validated.

Additionally, the previous changes broke compilation of `internal/identity/application/service.go` because the service layer was not updated to match the new signatures, and the integration tests still used the original base-method signatures.

## Session Repository Design

The session repository now exposes a **two-level API**:

### 1. Base Methods (no `organization_id` required)

These methods perform unscoped lookups and are used when organization context is legitimately unavailable:

| Method | Use Case |
|--------|----------|
| `FindByID(ctx, sessionID)` | Logout flow, tests |
| `FindActiveByUserID(ctx, userID)` | Tests |
| `FindByRefreshTokenHash(ctx, hash)` | Refresh-token flow (pre-authentication) |
| `Revoke(ctx, sessionID)` | Logout flow, tests |
| `RevokeAllByUserID(ctx, userID)` | Tests |
| `RevokeAllByUserIDTx(ctx, tx, userID)` | Transactional use (currently unused) |
| `MarkUsed(ctx, sessionID)` | Tests |

### 2. Organization-Aware Methods (`ForOrganization` suffix)

These methods add a database-level `organization_id` constraint for defense-in-depth:

| Method | Use Case |
|--------|----------|
| `FindByIDForOrganization(ctx, sessionID, organizationID)` | Auth middleware (`AuthRequired`) |
| `FindActiveByUserIDForOrganization(ctx, userID, organizationID)` | Admin session listing (future) |
| `RevokeForOrganization(ctx, sessionID, organizationID)` | Scoped revocation with org constraint |
| `RevokeAllByUserIDForOrganization(ctx, userID, organizationID)` | Password-change session invalidation |
| `RevokeAllByUserIDTxForOrganization(ctx, tx, userID, organizationID)` | Transactional scoped revocation (future) |
| `MarkUsedForOrganization(ctx, sessionID, organizationID)` | Auth middleware (`AuthRequired`) |

## Caller Classification

| Caller | Flow | Organization ID Available? | Method Used |
|--------|------|---------------------------|-------------|
| `AuthRequired` middleware | Authenticated request | Yes (from JWT claims) | `FindByIDForOrganization`, `MarkUsedForOrganization` |
| `RefreshToken` service | Refresh-token flow | No (only hash known) | `FindByRefreshTokenHash` (base) → validates at service layer |
| `Logout` service | Logout flow | No (sessionID from context) | `FindByID`, `Revoke` (base) → validated by middleware |
| `ChangePassword` service | Password change | Yes (`user.OrganizationID`) | `RevokeAllUserSessions` → `RevokeAllByUserIDForOrganization` |
| Integration tests | Test scenarios | Varies | Both base and org-aware methods as appropriate |

## Security Reasoning

### Defense-in-Depth Without Breaking Flows

The two-level design provides defense-in-depth while preserving legitimate authentication flows:

1. **Refresh-token flow**: Uses base `FindByRefreshTokenHash` because only the hash is available. After lookup, the service layer validates:
   - Session is not revoked (`session.IsRevoked()`)
   - Session is not expired (`session.IsExpired()`)
   - Session belongs to the correct user (`FindByID` on user repo)
   - Session organization matches the user's organization

2. **Auth middleware**: Uses org-aware `FindByIDForOrganization` because the JWT claims contain `organization_id`. The database query adds `AND organization_id = $2`, preventing cross-tenant session lookup even if the JWT is tampered with.

3. **Password-change invalidation**: Uses `RevokeAllByUserIDForOrganization` because `user.OrganizationID` is available from the `ChangePasswordParams`.

4. **Logout**: Uses base `Revoke` because the service method only receives a `SessionID`. The session has already been validated by `AuthRequired` middleware before the handler calls `Logout`.

### Security Properties Preserved

- **Session ownership**: Validated in middleware (`session.UserID.String() == userID`) and service layer.
- **User/session relationship**: Validated after base lookup in refresh-token flow.
- **Organization/tenant isolation**: Enforced at database level in org-aware methods; validated in service layer for base methods.
- **Revoked-session rejection**: Checked in middleware and service layer.
- **Expired-session rejection**: Checked in middleware and service layer.
- **Refresh-token rotation**: Preserved via `Update` after `FindByRefreshTokenHash`.
- **Refresh-token reuse detection**: Preserved via token-family validation in `RefreshToken`.
- **JTI validation**: JTI (session ID) validated against session record in middleware.
- **Logout/revocation**: Base `Revoke` used in logout; org-aware `RevokeForOrganization` available for scoped use.
- **Role-change session invalidation**: `RevokeAllUserSessions` now uses org-aware method.
- **Cross-tenant rejection**: Enforced by `RequireSameTenant` middleware AND org-aware repository methods.

## Remaining Limitations

1. **E2E tests in `test/e2e/`** — These Go-based e2e tests were already failing before this stage (verified by running against HEAD~1). They fail with 401 Unauthorized on all authenticated endpoints after successful login. This is a **pre-existing issue** unrelated to session repository changes.

2. **`RevokeAllByUserIDTxForOrganization`** — Added to the interface for completeness but currently has no production callers. It is available for future transactional use.

3. **`FindActiveByUserIDForOrganization`** — Added to the interface but currently has no production callers. It is available for future admin session-listing endpoints.

4. **Logout service-layer validation** — The `Logout` method relies on `AuthRequired` middleware to validate the session before the handler calls the service. For defense-in-depth, the service could validate the session's user/organization match itself, but this would require changing the `LogoutParams` struct and the API handler.
