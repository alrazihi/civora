## 1. Overview

This document describes the AI-assisted case observation capability implemented in Stage 6 of CIVORA 0.8. The system surfaces potentially useful observations about a case — including missing information, inconsistencies, relevant evidence, and incomplete documentation — without allowing those observations to silently become facts or decisions.

All observations are AI-generated and stored with `status = OPEN`. They require explicit human review via Accept, Reject, Correct, or Dismiss before being considered final.

## 2. Observation Model

### 2.1 Observation Entity

```go
type Observation struct {
    ID                uuid.UUID
    OrganizationID    uuid.UUID
    CaseID            *uuid.UUID       // nil for evidence-level observations
    EvidenceID        *uuid.UUID       // nil for case-level observations
    Type              ObservationType
    Source            ObservationSource // AI_MODEL or HUMAN
    Status            ObservationStatus
    Model             *ModelInfo
    Content           map[string]any
    Confidence        *float64          // 0.0-1.0
    Statement         string            // human-readable observation text
    SourceReferences  []SourceReference // links to evidence, forms, documents
    InputHash         string            // SHA-256 of inputs
    OutputHash        string            // SHA-256 of AI output
    CreatedAt         time.Time
    CreatedBy         *uuid.UUID
    ReviewedAt        *time.Time
    ReviewedBy        *uuid.UUID
    ReviewNotes       string
}
```

### 2.2 Observation Types

| Type | Description |
|------|-------------|
| **SUMMARY** | General summary of evidence or case |
| **ENTITY_EXTRACTION** | Named entities extracted from documents |
| **CLASSIFICATION** | Classification of evidence or case |
| **INCONSISTENCY** | Conflicting information between sources |
| **MISSING_INFORMATION** | Required evidence or data is absent |
| **RELEVANT_EVIDENCE** | Evidence that may be relevant but is not linked |
| **INCOMPLETE_DOCUMENTATION** | Documents missing required content or metadata |

### 2.3 Lifecycle States

| Status | Description |
|--------|-------------|
| **OPEN** | Awaiting human review (default for new AI observations) |
| **PENDING_REVIEW** | Legacy alias for OPEN (backward compatibility) |
| **ACCEPTED** | Human reviewer accepted the observation |
| **REJECTED** | Human reviewer rejected the observation |
| **CORRECTED** | Human reviewer corrected the observation |
| **DISMISSED** | Human reviewer dismissed as not applicable |

### 2.4 Source References

```go
type SourceReference struct {
    Type string // "evidence", "form_submission", "document"
    ID   string // UUID of the referenced resource
}
```

### 2.5 Validation Rules

- `OrganizationID` required (non-nil UUID)
- Either `CaseID` or `EvidenceID` must be provided
- `Type` must be one of the 7 allowed observation types
- `Confidence` must be in range [0.0, 1.0] if present
- `Content` size ≤ 100,000 bytes
- `Statement` max length 10,000 characters
- `ReviewNotes` max length 5,000 characters
- `InputHash` and `OutputHash` required for reproducibility

## 3. Detection Logic

### 3.1 Case-Level Detection

The `GenerateCaseObservations` method analyzes the full case context:

1. Retrieves all evidence for the case via `EvidenceRepository.FindByServiceRequest`
2. Retrieves all form submissions via `FormSubmissionRepository.ListByCase`
3. Builds structured case facts from evidence metadata and form data
4. Sends facts to the AI provider with detection-specific instructions
5. Parses results into typed observations with source references

### 3.2 Detection Categories

The AI provider prompt instructs the model to detect:

1. **MISSING_INFORMATION**: Required evidence types absent for the case service type
2. **INCONSISTENCY**: Conflicting values between form submissions and document content
3. **RELEVANT_EVIDENCE**: Evidence items that may be relevant but lack proper linkage
4. **INCOMPLETE_DOCUMENTATION**: Documents missing required fields, metadata, or content

### 3.3 Evidence-Level Detection (Legacy)

The existing `GenerateObservations` method continues to operate at the evidence level, analyzing document content for summaries, entities, and classifications. This path remains unchanged for backward compatibility.

## 5. Security

### 5.1 Authorization

All endpoints require:
1. `AuthRequired` — valid JWT
2. `RequireSameTenant` — JWT org_id matches URL org_id
3. `RequireAnyRole("admin", "staff")` — authorized role
4. Service-layer `UserChecker.BelongsToOrganization` — double-check

### 5.2 Tenant Isolation

- All database queries scoped by `organization_id`
- Case facts built only from tenant-scoped evidence and forms
- No cross-tenant data leakage possible

### 5.3 Observation Boundary

Observations are **never** used to:
- Modify forms or evidence
- Change rules or workflow state
- Approve, reject, or transition cases
- Create final decisions

They are surfaced for human review only.

## 8. Security

### 8.1 Observation Non-Authoritative Boundary

AI observations are explicitly non-authoritative. The system enforces this by:

1. Observations cannot trigger workflow transitions
2. Observations cannot modify forms, evidence, or rules
3. Observations cannot approve/reject cases
4. All observation status changes require explicit human action
5. Audit trail records all observation lifecycle events

### 8.2 Cross-Tenant Isolation

- All queries filtered by `organization_id`
- Case facts built only from tenant-scoped sources
- No tenant data leaks through observation content

### 8.3 Malicious Document Handling

- Document content capped at 100KB before sending to provider
- PII sanitization applied before external provider calls
- Checksum validation ensures document integrity
- Provider errors do not leak sensitive data
