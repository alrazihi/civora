## 2. Goal

Create a **provider-neutral AI abstraction** that decouples CIVORA's core
domain from any specific AI vendor. The abstraction must support:

- **hosted AI providers** (OpenAI)
- **local models** (Ollama, llama.cpp)
- **self-hosted inference** (OpenAI-compatible local servers)
- **future providers** (Anthropic, Google, HuggingFace) via a drop-in contract
- **no-AI operation** (`NoopProvider`, AI off by default)

The exact providers are secondary; the **CIVORA architecture is primary**.

---

## 3. Architecture

The AI module follows the existing modular-monolith / clean-architecture
convention (`internal/<module>/domain | application | api | infrastructure`):

```
                 ┌───────────────────────┐
   domain  ◄─────│  ObservationEntity    │      (pure, no I/O)
                 │  AIProvider interface  │
                 │  VerifiedFactEntity    │
                 └───────────▲────────────┘
                             │ uses
                 ┌───────────┴───────────┐
   application ◄─│ AIService             │  Application service
                 │  - GenerateObservations│  (orchestration + txns)
                 │  - ReviewObservation   │
                 │  - VerifyFact          │
                 │  - DocumentContentPort │
                 │  - PIISanitizerPort    │
                 └───────────▲───────────┘
                             │ calls
   infrastructure             │
   ┌──────────────────────────┴──────────────────────────┐
   │ providers/               guard/                    │
   │  openai.go (OpenAICompat) prompt_injection_guard.go │
   │  local.go  (wraps OpenAICompat, SkipAuth)            │
   │  noop.go   (safe-fail default)                       │
   │ postgres/ (ObservationRepository, VerifiedFactRepo)  │
   │ adapter/ (DocumentContentProvider ← evidence)        │
   │ sanitizer/ (PIIRedactor)                             │
   └──────────────────────────────────────────────────────┘
```

Key properties of the boundary:

- The domain exposes **ports** (`AIProvider`, `ObservationRepository`,
  `VerifiedFactRepository`, `DocumentContentProvider`, `PIISanitizer`).
- Provider-specific types (`openAIRequest`, `openAIMessage`,
  `responseFormat`, `openAIResponse`) live entirely behind the
  `OpenAIProvider` struct and **never** cross the domain/application boundary.
- `ModelInfo` (name/version/provider) is the **only** model metadata the
  domain retains, enabling future providers to be swapped without domain
  changes.
- `internal/ai/` has **no import path** into `internal/decisions/`,
  `internal/workflow/`, or `internal/rules/application/`. The safety boundary
  is enforced by import-graph isolation, not by convention.

## 4. Interfaces

### 4.1 Provider contract (`internal/ai/application/service.go`)

```go
type AIProvider interface {
    GenerateObservations(ctx context.Context, req ProviderRequest) ([]ObservationResult, error)
    ProviderInfo() domain.ModelInfo
}

type ProviderRequest struct {
    OrganizationID uuid.UUID
    EvidenceID     uuid.UUID          // nullable when CaseID is provided
    CaseID         *uuid.UUID         // case-level observations
    Documents      []domain.DocumentContent
    CaseFacts      []map[string]any
    Options        domain.ProviderOptions
}

type ObservationResult struct {
    Type       domain.ObservationType
    Content    map[string]any
    Confidence *float64
    InputHash  string
    OutputHash string
    Model      domain.ModelInfo
}
```

### 4.2 Provider selection (`cmd/civora/main.go`)

A `switch` on `cfg.AI.Provider` selects exactly one provider at startup:

```go
switch {
case cfg.AI.Enabled && cfg.AI.Provider == "openai" && cfg.AI.OpenAIAPIKey != "":
    aiProvider = aiprovider.NewOpenAIProvider(...)
case cfg.AI.Enabled && cfg.AI.Provider == "local" && cfg.AI.LocalEnabled:
    aiProvider = aiprovider.NewLocalProvider(...)
default:
    aiProvider = aiprovider.NewNoopProvider()
}
```

The `NoopProvider` is the **default** whenever AI is disabled or unconfigured,
implementing safe-fail:
`var ErrProviderDisabled = errors.New("AI provider is not configured or is disabled")`.

### 4.3 Providers

| Provider | File | Protocol | Default |
|---|---|---|---|
| `OpenAIProvider` | `infrastructure/provider/openai.go` | OpenAI Chat Completions (`POST /chat/completions`) | no (needs key) |
| `LocalProvider` | `infrastructure/provider/local.go` | wraps `OpenAIProvider` with `SkipAuth`, OpenAI-compatible local servers (Ollama/llama.cpp) | no |
| `NoopProvider` | `infrastructure/provider/noop.go` | returns `ErrProviderDisabled` | yes |

`ModelInfo` returned per provider:
- OpenAI: `{Name: cfg.model, Version: "1.0", Provider: "openai"}`
- Local:  `{Name: model, Version: "1.0", Provider: "local"}`
- Noop:   `{Name: "noop", Version: "0.0.0", Provider: "local"}`

### 4.4 Response validation

Before parsing, the `OpenAIProvider` runs the LLM response through a
`PromptInjectionGuard` (`internal/ai/infrastructure/guard`):

- `ValidateResponse` strips non-JSON prefix/suffix, validates JSON, and rejects
  responses containing known prompt-injection instruction patterns
  ("ignore previous instructions", "forget your instructions", "system prompt",
  "jailbreak", etc.).
- `ValidateObservationResult` rejects observations whose content keys match
  suspicious patterns (`instruction`, `command`, `system`, `prompt`, `override`,
  `jailbreak`, `role`, `behavior`).

These guards run **inside the provider**, so a malformed or hostile provider
response is never persisted as an observation.

## 5. Provider boundary

The boundary is a single interface: `AIProvider` in
`internal/ai/application/service.go`. The application layer (`AIService`)
depends on the **abstraction only**; it never imports a provider package.

- Provider construction lives in `cmd/civora/main.go` (composition root).
- Providers depend on `internal/ai/application` (for `ProviderRequest`/
  `ObservationResult`) and `internal/ai/domain` (for `ModelInfo`/
  `DocumentContent`) — **never the reverse**.
- No provider package imports the application service, so adding a new provider
  cannot alter orchestration.

Provider-specific configuration remains behind the abstraction: API keys, base
URLs, models, timeouts, temperature, and response formats are all fields of
`OpenAIProviderConfig` / `LocalProvider` construction, never surfaced through
domain types.

### Metadata captured per observation

| Field | Source |
|---|---|
| `model.name`, `model.version`, `model.provider` | `ProviderInfo()` |
| `input_hash` | SHA-256 of document content + ids + types + max_tokens |
| `output_hash` | SHA-256 of the raw provider response body |
| `confidence` | from provider result (default 0.5 if absent) |
| `created_at` | server UTC timestamp |
| `request/reference ID` | propagated via `shared.RequestIDFromContext` in audit events |
| `actor_id` | the human who triggered generation (audit only, not stored on entity) |

Prompts and case data are **not** logged. Only hashes and model metadata are
stored, in keeping with the "no unnecessary PII/data retention" rule.

## 7. Failure behavior

AI must fail **safely**. The application layer guarantees:

- A provider error or `ErrProviderDisabled` returns
  `ErrAIProviderUnavailable` (HTTP 503) and records an
  `ai.observation.failed` audit event.
- **No observation is persisted on failure.** The generate flow only persists
  after a successful provider response, inside a single `database.InTransaction`
  that wraps every `ai.observation.created` audit event and every
  `repo.SaveTx` — so a partial failure rolls back all audit + domain writes
  for that generation.
- `ReviewObservation` wraps `UpdateStatusTx` + audit in the same transaction.

Failure modes handled:

| Failure | Behavior |
|---|---|
| Provider unavailable / offline | `ErrAIProviderUnavailable`; no persistence |
| Timeout (HTTP client timeout) | HTTP error → `ErrAIProviderUnavailable` |
| Malformed provider response (non-JSON) | `PromptInjectionGuard`/JSON error → provider error |
| Invalid structured response (non-JSON object / missing array) | parse error → `ErrAIProviderUnavailable` |
| Invalid observation type from provider | observation dropped by `isValidObservationType` |
| Empty response (no choices / no observations) | error returned, no observations |
| Authentication failure (401) | non-200 status → error |
| Rate limiting (429) | non-200 status → error |
| Partial failure during persistence | transaction rolled back; audit and observations stay consistent |

AI failure **never**:
- approves a case
- rejects a case
- transitions workflow state
- corrupts case data

Observations always start in a reviewable status and require explicit human
accept/correct/reject/dismiss before becoming a `VerifiedFact`.

## 8. Security

- **Tenant isolation**: all `ai_observations`/`ai_verified_facts` queries are
  scoped by `organization_id` at the repository layer; the handler enforces
  `RequireSameTenant` + `RequireAnyRole("admin","staff")`; `AIService` calls
  `userChecker.BelongsToOrganization` for the actor on every operation.
- **PII / document security**: documents are retrieved via the evidence
  service's streaming endpoint (which itself enforces tenant scoping and
  records an audit event); `PIISanitizer` redacts SSNs, credit-card numbers,
  emails, and phone numbers from text-like content before provider calls; raw
  document bytes are never logged.
- **Prompt injection**: `PromptInjectionGuard` validates provider responses;
  the system prompt instructs the model to treat document content as data, not
  instructions.
- **Prompt versioning**: no template system exists; this is a known limitation.
- **API key handling**: keys are read from env at startup only; never stored in
  the DB; never serialized into observations.
- **No internal leakage**: `Document.StorageKey` is `json:"-"` and is never
  exposed through the AI module; only document metadata (id, filename, content
  type, checksum) and content are passed to providers.

## 9. Tests

Provider abstraction tests use **test doubles only at the infrastructure
boundary**:

- `internal/ai/infrastructure/provider/openai_test.go` — uses
  `httptest.NewServer` to mock LLM endpoints (success, no-documents, no-key,
  API errors, request limits, empty observations, skip-auth). No real network
  or external calls.
- `internal/ai/infrastructure/provider/local_test.go` — same `httptest` pattern
  for the local provider.
- `internal/ai/infrastructure/provider/noop_test.go` — confirms the safe-fail
  default always returns `ErrProviderDisabled`.
- `internal/ai/infrastructure/guard/prompt_injection_guard_test.go` — injection
  patterns and malformed responses.
- `internal/ai/application/service_test.go` — uses in-memory mock repos and a
  mock `AIProvider` (no fake LLM behavior in production logic).

Test doubles are **not** built into production logic; providers call the real
HTTP path against `httptest` servers, and the application service depends on the
`AIProvider` interface.

## 10. Known limitations

1. **No per-organization provider routing.** Selection is global env config;
   one provider is active at a time, not per-tenant or per-evidence-type.
2. **No model version pinning beyond config.** Provider default-model changes
   upstream change behavior unless the operator pins `CIVORA_AI_*_MODEL`.
3. **No usage/token budget or rate limiting on AI calls** beyond the global
   HTTP rate limiter.
4. **Non-deterministic generation.** Temperature is 0.3; identical inputs
   produce different outputs. Reproducibility is supported via input/output
   hashes but not byte-exact replay.
5. **No prompt template/versioning system.** System/user prompts are hardcoded
   strings.
6. **No automatic retry or circuit breaker.** Provider failures return
   immediately; no queued retry.

## 13. Verdict

**GO**

The provider-neutral AI abstraction is implemented and integrated. The domain
depends only on the `AIProvider` port; hosted, local, self-hosted, future, and
no-AI providers are all supported through a single contract. All five Stage 1
blockers are resolved (verified facts and schema updates landed after them),
AI is off by default, `NoopProvider` is the safe-fail default, failures never
affect decisions/workflow/case data, and the provider boundary is clean.

Known limitations (no per-org routing, no model pinning, no retry/circuit
breaker, no prompt versioning) are documented and do not block Stage 2.
